## Summary

Improve `Onnxify.Safetensors` with a more user-friendly public API for common safetensors workflows.

The package should remain capable of low-level archive and tensor storage work, but typical users should be able to load, inspect, retrieve, create, and save safetensors files with clear method names, typed tensor access, good errors, and minimal boilerplate.

## Depends On

- Existing `Onnxify.Safetensors` archive, metadata, and tensor storage APIs.
- Existing tests and examples for reading and writing safetensors files.
- Current package documentation in `.docs/nuget/Onnxify.Safetensors.md`.
- Any porting notes for parity with `third_party/safetensors`.

## Enables

- Easier adoption of safetensors support without reading internal archive details.
- Cleaner examples for model-weight loading and conversion workflows.
- Better integration points for `Onnxify.HuggingFace`, `Onnxify.TorchSharp`, and future model import/export flows.
- More actionable diagnostics for malformed files, missing tensors, dtype mismatches, and shape mismatches.

## Goals

- Audit the current public API and identify common tasks that require too much boilerplate.
- Add high-level load/save entry points for files and streams, including async variants where consistent with the package.
- Provide ergonomic tensor lookup APIs by name, including typed retrieval with dtype and shape validation.
- Make metadata access easy for both global metadata and per-tensor metadata.
- Provide simple creation APIs for building safetensors archives from named tensors and metadata.
- Improve error messages for missing tensors, unsupported dtypes, invalid shapes, duplicate names, malformed headers, and data-length mismatches.
- Preserve lower-level APIs for advanced callers.
- Update examples, NuGet docs, and release notes if the public API changes.

## Non-Goals

- Do not rewrite the safetensors file format implementation unless API work exposes a correctness issue.
- Do not couple `Onnxify.Safetensors` directly to TorchSharp or ONNX Runtime unless the dependency is already intentional.
- Do not remove existing public APIs without a compatibility plan.
- Do not hide validation failures by silently converting unsupported dtypes or reshaping tensor data.
- Do not require network access or Hugging Face APIs for core safetensors usage.

## Candidate API Shape

Evaluate high-level methods such as:

```csharp
var archive = SafetensorsArchive.Load("model.safetensors");
var weights = archive.GetTensor<float>("encoder.layer.0.weight");
var metadata = archive.Metadata;

archive.Save("updated.safetensors");
```

And creation helpers such as:

```csharp
var archive = SafetensorsArchive.Create()
    .AddTensor("weight", tensor)
    .WithMetadata("format", "pt");
```

Exact names should follow the existing package style and avoid introducing builder APIs unless they materially reduce complexity.

## Implementation Steps

1. Inspect current `Onnxify.Safetensors` public APIs and tests to identify the friction points.
2. Compare common safetensors usage patterns from existing examples and package consumers.
3. Choose the public API shape for:
   - file loading
   - stream loading
   - async loading
   - tensor lookup
   - typed tensor materialization
   - archive creation
   - metadata access
   - save/write operations
4. Implement high-level APIs as thin layers over the existing validated low-level implementation.
5. Add clear exception types or error messages for common user mistakes.
6. Add focused tests for success paths and diagnostics.
7. Update examples and NuGet docs with concise before/after usage.
8. Update release notes for `Onnxify.Safetensors`.

## Tests

Add or update tests for:

- loading safetensors from a file path
- loading safetensors from a stream
- async load/save behavior if implemented
- retrieving a tensor by name
- typed tensor retrieval with matching dtype
- typed tensor retrieval with dtype mismatch diagnostics
- missing tensor diagnostics
- shape mismatch diagnostics
- creating an archive from named tensors
- preserving global metadata through save/load
- duplicate tensor name handling
- invalid or malformed safetensors input diagnostics
- existing low-level APIs continuing to work

## Acceptance Criteria

- Common read, inspect, tensor lookup, create, and save workflows are available through concise public APIs.
- Typed tensor retrieval validates dtype and shape expectations where applicable.
- Error messages for common failure modes are actionable.
- Existing lower-level APIs remain available or have a documented migration path.
- Focused tests cover the new ergonomic API and representative failure cases.
- NuGet docs and release notes describe the improved API with runnable examples.

## Risks

- Adding convenience APIs can accidentally duplicate or bypass existing validation. Keep them layered on top of the proven core implementation.
- Typed tensor helpers may require careful memory ownership and allocation decisions.
- Too many overloads can make the API harder to learn. Prefer a small set of clear entry points.
- Compatibility with existing callers matters if names overlap with current APIs.
