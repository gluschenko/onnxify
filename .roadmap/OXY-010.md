# OXY-010: ModelGenerator Shared Generated Base Classes

| Field | Value |
| --- | --- |
| Status | DONE |
| Estimated complexity | 40 human-hours |
| Created | 2026-06-27 |
| Last modified | 2026-06-27 |

## Summary

Change `Onnxify.ModelGenerator` so generated model implementations inherit shared generated abstract base classes instead of repeating private helper methods, utilities, and runtime plumbing in every generated model class.

The generator currently has to emit implementation details into each generated class. This task should move reusable helper code into one generated base class per export/runtime mode:

- one abstract base class for `OnnxInferenceSession`-style generated wrappers
- one abstract base class for generated TorchSharp `TorchModule` reconstruction/export surfaces

Each base class should be emitted at most once per consuming compilation, and only when at least one connected model actually uses that generation mode.

## Depends On

- Existing `Onnxify.ModelGenerator` source generator pipeline.
- Existing generated `OnnxInferenceSession` wrapper shape.
- Existing or planned generated TorchSharp `TorchModule` output shape.

## Enables

- Smaller generated files for projects with many ONNX models.
- Easier maintenance of shared generated runtime helpers.
- Cleaner generated model implementations focused on model-specific inputs, outputs, metadata, and graph/module shape.
- Future changes to common generated behavior without duplicating edits across multiple printers.

## Goals

- Introduce one shared abstract generated base class for `OnnxInferenceSession` generated implementations.
- Introduce one shared abstract generated base class for TorchSharp `TorchModule` generated implementations.
- Make each generated model class inherit the appropriate abstract base class for its generation mode.
- Emit each abstract base class once per consuming project compilation, not once per model.
- Do not emit a base class for a generation mode that is not used by any connected model.
- Move private helper methods, utility functions, repeated conversion helpers, name sanitization helpers, runtime guards, and other non-model-specific implementation details into the appropriate abstract base class.
- Keep model-specific generated classes responsible only for model-specific contracts, metadata, wiring, and overrides.
- Store the base class source in normal editable `.cs` files inside `src/Onnxify.ModelGenerator`, not as large string literals.
- Add build/package wiring so those `.cs` template files are available to the generator implementation but do not ship as runtime DLL dependencies in the NuGet package.

## Non-Goals

- Do not change the public shape of generated model input/output DTOs unless required by inheritance.
- Do not merge the `OnnxInferenceSession` and TorchSharp generation modes into one base class.
- Do not add a runtime assembly dependency for helper code that should remain generated source.
- Do not emit unused base classes just because `Onnxify.ModelGenerator` supports that mode.
- Do not move model-specific ONNX metadata into the shared base classes.
- Do not redesign the `.onnx` discovery or `OnnxModel` MSBuild item flow.

## Proposed Shape

Use two generated abstract classes with stable internal generated names. Names can be adjusted to match existing namespace conventions, but should make the runtime mode clear.

Suggested names:

```csharp
internal abstract class OnnxInferenceSessionModelBase
{
    // Shared ONNX Runtime wrapper helpers.
}

internal abstract class TorchModuleModelBase
{
    // Shared TorchSharp module generation helpers.
}
```

Generated model classes should inherit the mode-specific base:

```csharp
public sealed partial class BertClassifierModel : OnnxInferenceSessionModelBase
{
}

public sealed partial class BertClassifierTorchModule : TorchModuleModelBase
{
}
```

If generated classes live in user namespaces, either:

- emit the base classes into the same generated namespace as the affected model classes when only one namespace is used, or
- emit them into a deterministic generated support namespace and fully qualify inheritance when multiple generated namespaces are present.

Prefer a deterministic generated support namespace if the current generator can produce wrappers in multiple user namespaces in one project.

## Editable Template Source

The abstract base classes should exist as normal `.cs` files in the generator source tree, for example:

```text
src/Onnxify.ModelGenerator/Templates/OnnxInferenceSessionModelBase.cs
src/Onnxify.ModelGenerator/Templates/TorchModuleModelBase.cs
```

Maintainers should be able to edit these files with normal C# syntax highlighting, formatting, navigation, and compiler feedback where practical.

Avoid maintaining these classes as manually escaped string literals. If placeholder substitution is needed, keep it minimal and explicit.

Potential approaches:

- include the template `.cs` files as embedded resources in `Onnxify.ModelGenerator`
- include the template `.cs` files as additional files consumed by the generator project itself
- use a small template loader that reads embedded source text and applies deterministic namespace/type-name substitutions

If Roslyn parsing or formatting packages are added to make this maintainable, mark them with `PrivateAssets="all"` and restrictive `IncludeAssets` so they support generator development/build only and do not appear as transitive runtime DLLs for package consumers.

## Conditional Generation

Before emitting shared support sources, the generator should collect the required generation modes for the current compilation.

Rules:

- If at least one model generates an `OnnxInferenceSession` wrapper, emit the ONNX Runtime base class once.
- If at least one model generates a TorchSharp `TorchModule` wrapper, emit the TorchModule base class once.
- If no model uses a mode, emit no base class for that mode.
- If both modes are used, emit both base classes.
- Generated source hint names must be stable and collision-free.

Suggested hint names:

```text
Onnxify.ModelGenerator.OnnxInferenceSessionModelBase.g.cs
Onnxify.ModelGenerator.TorchModuleModelBase.g.cs
```

## Implementation Steps

1. Inspect current generated `OnnxInferenceSession` code and identify repeated private methods/utilities that are safe to hoist.
2. Inspect current or planned TorchSharp `TorchModule` generated code and identify its repeated helper surface.
3. Create editable `.cs` template files for the two abstract base classes under `src/Onnxify.ModelGenerator`.
4. Add project-file wiring so template files are embedded or otherwise available to the source generator at analyzer runtime.
5. Add a small template/source loader instead of keeping large generated support classes in string literals.
6. Add generation-mode collection before source emission.
7. Emit each required base class once with stable hint names.
8. Update generated model printers so implementation classes inherit the appropriate base class.
9. Remove duplicated helper methods from per-model generated classes.
10. Ensure generated code remains deterministic across multiple models, multiple namespaces, and mixed generation modes.
11. Update package docs if generated code shape or diagnostics are user-visible.

## Packaging Rules

- Template support dependencies must not become runtime dependencies of projects that reference `Onnxify.ModelGenerator`.
- Any new Roslyn/template development dependency should use `PrivateAssets="all"`.
- If a dependency is only needed while building the generator package, constrain `IncludeAssets` to the required compile/build/analyzers assets.
- Verify the packed NuGet does not include unwanted helper DLLs from template tooling.
- Keep generated support code emitted as source into the consuming compilation, not as a separate runtime assembly.

## Tests

Add or update tests in `src/Onnxify.Tests/OnnxModelGeneratorTests.cs` for:

- one ONNX Runtime model emits exactly one ONNX Runtime base class
- multiple ONNX Runtime models still emit exactly one ONNX Runtime base class
- no ONNX Runtime model means no ONNX Runtime base class source is emitted
- one TorchModule model emits exactly one TorchModule base class
- multiple TorchModule models still emit exactly one TorchModule base class
- no TorchModule model means no TorchModule base class source is emitted
- mixed generation modes emit both base classes exactly once
- generated model classes inherit the correct base class
- generated model classes no longer duplicate hoisted private helpers
- projects with models in multiple namespaces compile
- generated code compiles in a consumer-style test project
- packed NuGet layout does not include unintended dependency DLLs for template tooling

If current tests assert exact generated source, update snapshots or assertions to account for the new support source files and smaller per-model implementations.

## Acceptance Criteria

- `Onnxify.ModelGenerator` emits shared abstract base classes for repeated generated runtime helpers.
- There are two separate base classes: one for `OnnxInferenceSession` generation and one for TorchSharp `TorchModule` generation.
- Each base class is emitted only when at least one connected model uses the corresponding generation mode.
- Each required base class is emitted once per compilation.
- Generated model classes inherit the correct base class.
- Repeated private helper code is removed from per-model generated classes.
- Base class source is maintained as normal `.cs` files in the generator project, not as large string literals.
- Added generator-side dependencies do not leak into the consumer-facing NuGet package as runtime DLLs.
- Focused generator tests cover conditional emission, inheritance, compilation, and packaging behavior.

## Risks

- Namespace selection can become tricky when one project generates models into several namespaces. Prefer a deterministic support namespace if needed.
- Moving helpers can accidentally change generated public API or accessibility. Keep base members `protected` or `private protected` only where derived models need them.
- Source-generator analyzers run from packaged assets, so template loading must work both from local builds and packed NuGet analyzer execution.
- Exact-source tests may become brittle. Prefer semantic assertions for inheritance and helper de-duplication where possible.
- Dependency packaging for analyzer projects is easy to get wrong. Verify the `.nupkg` contents explicitly.
