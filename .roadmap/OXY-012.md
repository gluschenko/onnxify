## Summary

Redesign `Onnxify.CLI` into a more consistent, feature-rich, and script-friendly command-line surface.

The current CLI should be reviewed as a product surface rather than only a thin test harness. The redesigned CLI should use predictable command patterns, expose the most useful repository/package workflows, and produce readable human output plus stable machine-readable output where appropriate.

## Depends On

- Existing `Onnxify.CLI` project structure and command registration.
- Current public APIs across `Onnxify`, `Onnxify.ModelGenerator`, `Onnxify.ProjectGenerator`, `Onnxify.HuggingFace`, and related packages.
- Existing package documentation and examples that mention CLI usage.

## Enables

- A more discoverable CLI for inspecting, validating, generating from, and transforming ONNX models.
- Better demos and smoke tests for the package family.
- Stable command shapes that future features can extend without breaking scripts.
- Clearer diagnostics when users run commands on invalid models, missing files, or unsupported workflows.

## Goals

- Audit the current `Onnxify.CLI` command set, option names, output behavior, and error handling.
- Define a consistent command grammar, including verbs, nouns, option naming, defaults, and exit-code behavior.
- Add or improve practical commands for model inspection, validation, conversion/generation workflows, and repository download scenarios where supported by existing packages.
- Support better output formatting, including concise terminal tables, detailed text output, and JSON output for automation.
- Make diagnostics readable and actionable, with clear file paths, model names, operator names, and suggested next steps where possible.
- Keep commands script-friendly: stable option names, deterministic output modes, nonzero exit codes on failures, and quiet/verbose controls.
- Update CLI documentation and package release notes when the public command surface changes.

## Non-Goals

- Do not redesign the underlying library APIs solely to make CLI implementation easier.
- Do not move experimental workflows into the CLI until the owning package behavior is stable enough to document.
- Do not make terminal formatting required for machine-readable output.
- Do not add network-dependent default behavior to commands that should work offline.
- Do not treat the CLI as a replacement for generated C# projects or typed runtime wrappers.

## Command Pattern Direction

Prefer a noun-oriented command hierarchy with clear verbs under each area. Candidate groups:

- `model inspect`
- `model validate`
- `model metadata`
- `model external-data`
- `generate project`
- `generate wrapper`
- `huggingface download`
- `torchsharp export` if the owning package surface is stable enough

Prefer long option names that read consistently across commands, for example:

- `--input`
- `--output`
- `--format`
- `--opset`
- `--include`
- `--exclude`
- `--overwrite`
- `--verbose`
- `--quiet`

Use short aliases only for high-frequency options where they are unambiguous.

## Output Formatting

Support at least:

- `text` for readable default terminal output.
- `json` for scripts and integration tests.
- `table` when a command naturally returns rows.

Formatting should be deterministic enough for tests. JSON output should avoid decoration, progress spinners, ANSI styling, or localized labels.

Terminal output should keep common failure modes visible without requiring `--verbose`. Verbose output can add stack traces, resolved paths, selected package versions, and low-level model details.

## Implementation Steps

1. Inspect the existing `Onnxify.CLI` project, command parser library, command names, option handling, and output helpers.
2. Inventory high-value workflows already supported by library APIs and decide which belong in the CLI now.
3. Write a command-pattern proposal in the task worklog before implementation if the redesign affects existing commands.
4. Introduce or refactor shared CLI output helpers for text, table, and JSON output.
5. Standardize error handling and exit-code behavior across commands.
6. Implement the first batch of redesigned commands with compatibility notes for any renamed or replaced commands.
7. Add focused tests that execute commands through the real parser rather than only testing helper methods.
8. Update README, CLI docs, NuGet docs, and release notes where public usage changes.

## Tests

Add or update tests for:

- command parser registration and help text for each public command group
- success exit codes for representative commands
- failure exit codes for missing files, invalid models, invalid options, and unsupported output formats
- deterministic JSON output
- readable table/text output for model inspection
- quiet and verbose behavior
- overwrite behavior for commands that create files
- compatibility or migration behavior for renamed commands, if existing commands change

## Acceptance Criteria

- The CLI has a documented command hierarchy and option naming convention.
- Redesigned commands cover the first useful batch of model inspection, validation, and generation workflows.
- Human-readable output is clean and useful by default.
- JSON output is stable and free of terminal decoration.
- Errors produce actionable messages and correct nonzero exit codes.
- Automated tests cover command registration, representative success paths, representative failure paths, and output formatting.
- Public docs and release notes reflect any changed or added CLI commands.

## Risks

- Renaming existing commands can break early users or local scripts. Preserve aliases or document migration where practical.
- Rich terminal output can make tests brittle if formatting is not centralized and deterministic.
- Commands that wrap multiple packages can blur ownership boundaries. Keep feature logic in owning libraries and use the CLI as orchestration.
- Network-backed workflows, especially repository downloads, can make tests flaky unless mocked or isolated.
