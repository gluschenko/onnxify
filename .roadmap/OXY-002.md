## Summary

Introduce the intermediate representation and scanner registry for decompiled TorchSharp `forward` methods.

This task creates the "syntax to IR" half of the future exporter, but only for a narrow subset of syntax. The old exporter remains as the behavioral fallback.

## Depends On

- `OXY-001`: metadata, diagnostics, and shape/type resolver foundation

## Enables

- `OXY-003`: printing the minimal IR into `OnnxGraph`
- `OXY-004`: migrating basic data-flow syntax

## Goals

- Add a typed deep export IR layer.
- Add scanner abstractions for statement and expression syntax.
- Add an ordered scanner registry.
- Scan a minimal forward method into IR without emitting ONNX nodes.
- Make scanner diagnostics structured and testable.
- Keep the old monolithic path available for non-migrated syntax.

## Non-Goals

- Do not print IR into ONNX yet, except for test-only inspection if useful.
- Do not migrate broad Torch operation coverage.
- Do not remove existing AST interpreter helpers.
- Do not expose scanner APIs publicly yet.

## Proposed Internal Layout

```text
DeepExport/
  Ir/
  Scanning/
    Statements/
    Expressions/
    Torch/
    Modules/
    Helpers/
```

## Core IR Types

### DeepExportNode

Every IR node should carry:

- stable node kind
- source syntax text or source location
- child nodes
- optional expected/result value category
- diagnostics anchor

### Statement Nodes

Initial required nodes:

- `BlockNode`
- `VariableDeclarationNode`
- `AssignmentNode`
- `ReturnNode`
- `ExpressionStatementNode`
- `UnsupportedStatementNode`

Stub or delayed nodes may be introduced for:

- `IfNode`
- `ForeachNode`
- `UsingScopeNode`
- `DeconstructionNode`
- `IgnoredValidationCallNode`

### Expression Nodes

Initial required nodes:

- `ParameterReferenceNode`
- `LocalReferenceNode`
- `MemberReferenceNode`
- `InvocationNode`
- `TensorMethodInvocationNode`
- `BinaryExpressionNode`
- `LiteralNode`
- `ArrayExpressionNode`
- `NullNode`

Stub or delayed nodes may be introduced for:

- `StaticMemberReferenceNode`
- `TorchInvocationNode`
- `ModuleForwardInvocationNode`
- `LocalHelperInvocationNode`
- `GeneratedHelperInvocationNode`
- `UnaryExpressionNode`
- `ConditionalExpressionNode`
- `CastExpressionNode`
- `IndexerExpressionNode`
- `InlineArrayExpressionNode`
- `TupleExpressionNode`

## Scanner Abstractions

Add internal scanner interfaces/base classes:

```csharp
internal interface IDeepExportScanner
{
    bool CanScan(DeepExportScanContext context, AstNode syntax);

    DeepExportNode Scan(
        DeepExportScanContext context,
        AstNode syntax
    );
}
```

Use generic base classes internally if helpful, but keep dispatch through a non-generic registry.

## Scanner Registry

`DeepExportScannerRegistry` must provide:

- deterministic ordered dispatch
- most-specific before generic matching
- clear no-match diagnostics
- test coverage for ambiguous invocation syntax

Initial scanner order should make tensor-specific invocation scanners run before generic invocation scanners.

## Minimal Syntax Coverage

The first scannable subset should cover a tiny module like:

```csharp
public override torch.Tensor forward(torch.Tensor input)
{
    var x = input.relu();
    return x;
}
```

Required syntax:

- method body block
- parameter references
- local variable declarations
- local references
- tensor method invocation node classification
- return statement

## Metadata Integration

Scanners may consult `DeepExportModuleMetadata` from `OXY-001` to classify member references, but they must not emit graph nodes or read runtime tensor values directly.

Rules:

- syntax recognition belongs in scanners
- runtime fact lookup belongs in metadata/resolver services
- graph emission belongs to later printers

## Fallback Strategy

Add an internal feature path that can scan a method and optionally retain the old monolithic export path.

Until `OXY-003` and `OXY-004` migrate enough behavior, public export should remain behaviorally identical by falling back to the old interpreter when a scanned path is incomplete.

## Tests

Add focused tests for:

- scanner registry ordering
- minimal forward method scans into expected IR shape
- unsupported statement produces structured diagnostic
- unsupported expression produces structured diagnostic
- tensor method invocation is classified before generic invocation
- metadata-backed member reference is represented as IR, not lowered directly

Use compact fixture modules in `src/Onnxify.Tests`.

## Acceptance Criteria

- Minimal forward body can be scanned into IR.
- The scanner layer emits no ONNX nodes.
- Public deep export behavior is unchanged for existing tests.
- Scanner diagnostics identify the syntax snippet and scanner stage.
- Old monolithic behavior remains available for non-migrated syntax.

## Risks

- Building too much IR at once will recreate the monolith in a new namespace. Keep this task intentionally small.
- Decompiler syntax can vary. Tests should assert semantic IR shape, not every raw syntax detail.
