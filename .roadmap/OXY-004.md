# OXY-004: Migrate Basic Deep Export Data Flow

| --- | --- |
| Status | REJECTED |

## Summary

Move the simplest real deep export behavior from the monolithic AST interpreter into scanners, IR nodes, and printers.

This task covers plain data flow only. It should make the new pipeline useful for straightforward methods without touching arrays, control flow, helper methods, modules, or broad Torch operation families.

## Depends On

- `OXY-001`: metadata foundation
- `OXY-002`: scanner and IR skeleton
- `OXY-003`: printer skeleton and minimal end-to-end path

## Enables

- `OXY-005`: shapes, arrays, tuples, and static control flow
- `OXY-006`: helpers and modules
- `OXY-007`: Torch operation families

## Goals

- Migrate basic statement-level data flow.
- Migrate local and member references.
- Migrate scalar literals and basic tensor/scalar arithmetic.
- Keep the old fallback for non-migrated syntax.
- Add focused scanner/printer tests for each migrated construct.

## Non-Goals

- Do not migrate array or tuple handling.
- Do not migrate helper methods.
- Do not migrate static branches, loops, or using scopes.
- Do not migrate broad Torch functional operations.
- Do not remove the old fallback.

## Scope

Migrate:

- method block execution
- parameter binding
- variable declarations
- assignments
- return statements
- expression statements where already supported by the minimal path
- local references
- member references backed by `OXY-001` metadata
- scalar literals
- null literals only where needed by existing basic expressions
- basic binary tensor/scalar arithmetic
- unary expressions that are already supported by existing tests and do not require extra syntax machinery

## Required IR Additions

Ensure these nodes are implemented end to end:

- `BlockNode`
- `ParameterReferenceNode`
- `LocalReferenceNode`
- `MemberReferenceNode`
- `VariableDeclarationNode`
- `AssignmentNode`
- `ReturnNode`
- `LiteralNode`
- `BinaryExpressionNode`
- `UnaryExpressionNode` if needed for existing behavior
- `NullNode` if needed for existing behavior

## Runtime Metadata Integration

Member references must use the metadata/reflection layer from `OXY-001`.

Rules:

- Scanners classify member access.
- Printers resolve member values through the metadata service.
- Scanners/printers must not introduce scattered raw reflection helpers.
- Runtime dimension or constant fields should flow through `DeepExportValue`, not raw `object`.

## Graph Emission

Printers should delegate to existing helpers where possible:

- `TorchTensorOperatorExtensions` for tensor arithmetic
- existing scalar initializer helpers through the new shape/type resolver

Avoid adding one-off ONNX node creation in basic expression printers when a helper already exists.

## Tests

Add focused tests for:

- variable declaration followed by return
- assignment rebinding
- parameter reference
- local reference
- member reference to a module field/property
- scalar literal initializer
- tensor + scalar
- tensor - scalar
- tensor * scalar
- tensor / scalar where current behavior supports it
- unsupported expression keeps fallback or emits a structured diagnostic in a test-only path

Validation requirements:

- structural graph assertions for emitted nodes
- ONNX Runtime session creation when executable
- TorchSharp eager vs ONNX Runtime parity for deterministic arithmetic

## Acceptance Criteria

- A simple data-flow-only `forward` method exports through the new scanner/printer path.
- Existing public deep export tests still pass.
- Basic data-flow constructs no longer depend on the old statement/expression interpreter.
- Reflection-backed member reads go through the metadata layer.
- Unsupported non-basic syntax still falls back or fails with stage-aware diagnostics, depending on the internal gate.

## Risks

- Basic expressions are deceptively broad. Keep this task to data flow and simple arithmetic.
- A partial migration can leave two implementations for the same construct. Delete old helper paths only when a construct is fully migrated.
