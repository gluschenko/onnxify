# OXY-029: Compiler Operator Mappings: Pointwise Operations And Broadcasting

## Summary

Add shared compiler mappings for deterministic elementwise operations and their supported TorchSharp spellings, including multidirectional broadcasting. The audited set covers arithmetic, numeric unary functions, comparisons, logical operators, pointwise selection, casts, and activations. Shape-changing, matrix, reduction, and nondeterministic operators remain in their own family tasks.

## Depends On

- [OXY-024](OXY-024.md).
- [OXY-034](OXY-034.md).

## Goals

- Select the supported pointwise set from the intersection of ONNXScript TorchLib converter cases and ONNX Runtime runtime tests before declaring completion.
- Implement mappings only in `Onnxify.Compiler` and preserve explicit constraints for supported overloads and broadcasting.
- Support tensor and representable scalar operands through compiler constants/ONNX initializers.
- ONNX `Mod` with default/floor remainder semantics is imported; TorchSharp `remainder` exports through `Div`/`Floor`/`Mul`/`Sub`, while the distinct TorchSharp `fmod` operation maps to ONNX `Mod(fmod=1)`.
- Keep unsupported signatures, dtypes, and known-incompatible broadcasting diagnostic; preserve generic unknown ONNX operators.
- Retain activation mappings already introduced by OXY-024/OXY-032 without duplicating their implementation.

## Audited Mapping Inventory

The currently implemented pointwise subset has the following ONNX identities. All entries are `Bidirectional` unless identified as one-way below.

- Arithmetic and numeric binary functions: `Add`, `Sub`, `Mul`, `Div`, `Pow`, `Max`, `Min`, `Mod`, `Fmod`, and `XLogY`.
- Numeric unary functions: `Abs`, `Neg`, `Exp`, `Expm1`, `Log`, `Sqrt`, `Floor`, `Ceil`, `Sin`, `Cos`, `Tan`, `Asin`, `Acos`, `Atan`, `Sinh`, `Cosh`, `Asinh`, `Acosh`, `Atanh`, `Erf`, `Erfc`, `Reciprocal`, `Round`, `RoundDecimals`, `Sign`, `Sinc`, and `Logit`.
- Comparisons and logical operations: `Equal`, `NotEqual`, `IsClose`, `Greater`, `GreaterOrEqual`, `Less`, `LessOrEqual`, `And`, `Or`, `Xor`, and `Not`.
- Pointwise selection, clipping, and type conversion: `Where`, `Clip`, `Cast`, `IsNaN`, `IsInf`, `IsFinite`, and `Heaviside`.
- Activations retained from OXY-024/OXY-032: `Celu`, `Elu`, `Gelu`, `HardSigmoid`, `HardSwish`, `LeakyRelu`, `Mish`, `PRelu`, `Relu`, `Selu`, `Sigmoid`, `Softplus`, `Softsign`, `Swish`, `Tanh`, and `ThresholdedRelu`.
- `Trunc` is `Bidirectional`; it lowers to ONNX `Mod` and `Sub` and is recovered from the exact two-node decomposition. `Frac` is `Bidirectional`; it lowers to `Abs`, `Floor`, `Sign`, `Mul`, and `Sub` and is recovered from that exact pattern. `NotEqual` is `Bidirectional`; it lowers to and imports exact `Equal` followed by `Not`. `Mod` imports only `fmod` unset/zero for remainder; `Fmod` separately imports/exports ONNX `Mod(fmod=1)` and maps TorchSharp `fmod` semantics.
- Composite pointwise mappings are `Bidirectional`: `Exp2` (`Pow`), `Log1p` (`Add`, `Log`), `Log10`/`Log2` (`Log`, `Div`), `LogAddExp`/`LogAddExp2`, `Lerp`, `AddCdiv`, `AddCmul`, `Deg2Rad`, `Rad2Deg`, `Rsqrt`, `Frac`, `Heaviside`, `XLogY`, `Logit`, `IsClose`, `Erfc`, `Expm1`, `RoundDecimals`, and `Sinc`. They use compiler-owned identities in `com.onnxify.compiler`; ONNX import recognizes the typed-node patterns and constants, and rejects pattern matches when internal values escape the matched subgraph. `LogAddExp` variants require the default `IsInf` detection attributes. `Heaviside` casts zero/one constants, `XLogY` casts zero, `Logit` casts its one/epsilon/clamp constants, and `IsClose` casts `rtol`/`atol` to the input dtype with standard `CastLike`, so Float16/32/64 share each lowering. The imported mappings print TorchSharp calls, and paired tests compile and execute generated C# against ONNX Runtime and eager TorchSharp results.

The paired runtime suite currently verifies Float32 for the ordinary arithmetic, unary, comparison, logical, activation, and `Where` cases; Boolean tensors for logical operators; Int32 `Where` and `Relu`; Float64/Int32/UInt8 `Add`; Int32 `Sub`, `Mul`, `Pow`, `Max`, `Min`, and `AddCmul`; Int64 `AddCmul`; UInt8 `Mul`, `Max`, and `Min`; Float16 `Div`, `Pow`, `Max`, and `Min`; Float32-base/Int32-exponent `Pow`; Int32 `Mod`; and Float32-to-Int64 `Cast`. `Add` validates known input types against the ONNXScript TorchSharp and ONNX Runtime CPU intersection: Float16/32/64, Int8/16/32/64, and UInt8 are accepted, while Boolean, complex, UInt16/32/64, and mixed input element types are rejected with diagnostics. `Sub` and `Mul` validate the common real numeric subset; `Mul` also accepts UInt8, while `Sub` rejects UInt8. `Max`/`Min` accept Float16/32/64, Int8/32/64, and UInt8; Boolean and complex require TorchLib's alternate logical/complex behavior, and Int16/UInt32 are outside the enabled CPU/converter intersection. `Pow` accepts Float16/32/64 and Int32/64 per input, with distinct allowed input dtypes because ONNX Runtime supports mixed numeric pairs; Float16 is accepted only when both inputs are Float16, and output dtype must match the base. Known types outside these intersections are rejected. `Div` accepts Float16/32/64 and rejects known non-floating types because TorchLib `aten_div` is restricted to `TFloat` and PyTorch promotes integer inputs, while ONNX `Div` retains integer output semantics. `Where` requires Boolean conditions and matching selected-value types; the CPU/TorchLib intersection is UInt8, Int32/Int64, Float32/Float64. `Clip`'s scalar bounds remain restricted to Float32, and known non-Float32 input tensors paired with such bounds are diagnosed. `Relu` accepts the audited CPU/TorchLib intersection Float16/32/64, Int8, and Int32; `Sigmoid` and `Tanh` accept Float32/64 on the CPU runtime. Known mismatches receive import diagnostics. These checks apply when ONNX graph metadata supplies the input types; unknown types remain deferred to downstream graph/runtime validation. Arithmetic scalar initializers are verified for Add/Sub/Mul/Div/Pow, including reversed scalar/tensor order for Sub and Div. Broadcasting is verified for tensor ranks one through three and statically incompatible dimensions. This is a tested representative dtype set, not a complete per-operator dtype matrix.

The audit includes these additional upstream cases from `third_party/onnxscript/tests/function_libs/torch_lib/ops_test_data.py`: `exp2`, `log1p`, `log10`, `log2`, `lerp`, `logaddexp`, `logaddexp2`, `addcdiv`, `addcmul`, `deg2rad`, `rad2deg`, and `rsqrt`. Their converter definitions are in `third_party/onnxscript/onnxscript/function_libs/torch_lib/ops/core.py` (functions `aten_exp2`, `aten_log1p`, `aten_log10`, `aten_log2`, `aten_lerp`, `aten_logaddexp`, `aten_logaddexp2`, `aten_addcdiv`, `aten_addcmul`, `aten_deg2rad`, `aten_rad2deg`, and `aten_rsqrt`). Runtime coverage uses ONNX Runtime CPU `math/element_wise_ops_test.cc` cases for the constituent `Pow`, `Log`, `Exp`, `Add`, `Sub`, `Mul`, `Div`, `Sqrt`, `Reciprocal`, `Less`, and `Where` operators.

Additional upstream pointwise candidates now implemented are `erfc`, `expm1`, and `sinc` from `ops_test_data.py` / `ops/special.py`, and `round_decimals` and `fmod` from `ops_test_data.py` / `ops/core.py`. They follow the respective TorchLib decompositions; `RoundDecimals` emits and imports a dtype-adaptive `CastLike` scale plus `Mul`/`Round`/`Div`, and also imports TorchLib's six-node `CastLike`/`Pow` sequence. `Sinc` recognizes both the simplified pattern and TorchLib's eight-node `CastLike` pattern. `Fmod` Float16/32/64, Int8/16/32/64, and UInt8 mappings have ONNX Runtime and eager TorchSharp parity; all listed types execute through generated TorchSharp and multidirectional broadcasting tests. `RoundDecimals` Float16/32/64 parity is covered. ONNX Runtime parity is tested for their supported CPU kernels, except Float64 `Erfc` because this runtime build has no `Erf(double)` kernel.

Explicit exclusions and boundaries:

- `RoundDecimals` imports its emitted `CastLike` scale pattern and TorchLib's `CastLike`/`Pow` sequence when all `CastLike` nodes use default `saturate=1` behavior. Patterns with non-default `CastLike` attributes are left generic. The scale starts as Float64 and is cast to the input type so emitted ONNX does not require compile-time dtype knowledge. Export requires Float16/Float32/Float64 inputs and rejects scales that overflow or underflow the known input dtype; unknown input dtype metadata is left for later graph validation.
- `Sinc` imports the TorchLib three-`CastLike` decomposition only when all `CastLike` nodes use default `saturate=1` behavior; other attribute variants are left generic.

- `atan2` (`aten_atan2` in ONNXScript `ops/core.py`, listed in `ops_test_data.py`) is excluded from exact decomposition. Its current TorchLib lowering maps every NaN result to zero, so NaN inputs and `atan2(±inf, ±inf)` differ from TorchSharp; signed-zero cases also require preserving `atan2(+0, -x) = +pi`. A focused test confirms TorchSharp returns NaN and ±pi/4 or ±3pi/4 for representative special values and that source scanning rejects the call rather than silently selecting the inexact lowering.
- `signbit` (`aten_signbit`) is excluded because the upstream `Less(x, 0)` decomposition cannot distinguish negative zero and also loses the sign bit of NaNs. A focused test confirms eager TorchSharp behavior for signed zero and positive/negative NaN, while compiler emission reports `Unsupported` rather than silently selecting the inexact pattern.
- `special.erfcx` is currently excluded from exact pointwise mappings because ONNXScript's `ops_test_data.py` marks its converter as expected-to-fail for numerical instability (issue 1223). Adding a decomposition without a stability analysis would only reproduce a known inaccurate result.
- `copysign` and `nan_to_num` are listed as pointwise-looking upstream functions but their `ops/core.py` converters raise `NotImplementedError`; they are not executable converter candidates in the current upstream inventory.
- `equal` is an all-elements reduction returning a scalar Boolean, not a pointwise comparison; it belongs to OXY-033. Pointwise `ne` is included as `NotEqual`.
- `fmod` is not equated with remainder: ONNX `Mod(fmod=1)` is handled by the separate `Fmod` mapping, while TorchSharp `remainder` retains its separately tested floor-remainder lowering.
- `div_mode` with `rounding_mode="trunc"` or `"floor"` is rejected with a source-span diagnostic. ONNX lowering differs for floating and integer input dtypes, but the TorchSharp source scanner receives tensors whose runtime dtype is not statically known; `rounding_mode=null` continues to use the ordinary `Div` mapping.
- `torch.add` and `torch.sub` map the two-operand/default-`alpha=1` form only. Explicit `alpha` arguments are rejected with a source-span diagnostic because the current binary mapping does not lower the TorchLib `Mul` plus `Add`/`Sub` decomposition. Tests cover constant and dynamic alpha forms.
- The new composite scan accepts scalar operands only when they are compile-time constants; dynamic scalar parameters are rejected with a source-span diagnostic. Most scalar-initializer composites currently support Float32 and Float64 tensor inputs only; `Exp2`, `Deg2Rad`, `Rad2Deg`, `Erfc`, `AddCdiv`, and `AddCmul` now also support Float16, as do `Heaviside`, `XLogY`, `Logit`, and `IsClose`. `AddCmul` additionally validates the signed integer types accepted by TorchLib `TReal` and the registered CPU arithmetic kernels. Float16 is explicitly rejected for `Log1p`, `Log10`, `Log2`, `Rsqrt`, `Lerp`, `LogAddExp`, and `LogAddExp2` where their component CPU kernels are not registered; focused diagnostics tests cover these cases.
- Compiler `Clip` scanning supports three-argument scalar `torch.clamp`/`Tensor.clamp` and scalar `torch.clamp_min`/`Tensor.clamp_min`/`torch.clamp_max`/`Tensor.clamp_max` forms with compile-time Float32 bounds. Tensor-valued clamp bounds lower to broadcastable `Max` then `Min` operations, matching `aten_clamp_tensor`; tensor overloads require tensor bounds or null, while scalar overloads require scalar bounds. Mixed tensor/scalar overloads are rejected.
- `FloorDivide` is an explicitly tested `ImportOnly` mapping. ONNX import recognizes `Div`→`Floor` for Float32/Float64, the signed integer correction decomposition from ONNXScript, and direct `Div` for unsigned types. `torch.floor_divide` source export and ONNX generation from the imported composite are rejected because the TorchSharp source scanner cannot specialize by runtime tensor dtype; ONNX `Floor` in this ONNX Runtime build is registered only for Float32/Float64.

These additions close several known candidate gaps but do not yet close the complete upstream inventory or the dtype matrix. Remaining work is a broader per-operator dtype/overload audit; `FloorDivide` is covered as an explicit one-way mapping with a runtime-typing export limitation. `IsFinite`, `Heaviside`, `XLogY`, `Logit`, and `IsClose` support Float16/32/64. The upstream `aten_isclose` candidate is currently an inexact converter: its own implementation notes a FIXME for `equal_nan` and compares via `Abs(self-other)`, which also fails for equal infinities. The compiler's default `isclose` mapping preserves exact equality and follows the `rtol=1e-5`, `atol=1e-8`, `equal_nan=false` formula; Float16 tests include the absolute tolerance underflow boundary at the minimum subnormal. `Logit` uses dtype-adaptive `CastLike` constants and supports null/default epsilon or compile-time numeric epsilon; dynamic epsilon gets a source-span unsupported diagnostic. Float16 `Logit` numerical parity allows one output ULP where ORT and TorchSharp round intermediate values differently. `XLogY` gives NaN precedence for `y=NaN`; this matches TorchSharp (`torch.xlogy(0, NaN)` is NaN), while the current ONNXScript decomposition's outer zero `Where` instead returns zero in that overlap case. The compiler emits/imports its corrected exact pattern and the runtime test covers that divergence.

## Tests

- Add paired ONNX-to-TorchSharp and TorchSharp-to-ONNX tests for each declared operator and supported broadcast case, including generated TorchSharp compilation/execution.
- Assert mapping identity/capability, graph or generated source structure, ONNX Runtime session creation, and deterministic numerical parity.
- Link each test to exact ONNXScript and ONNX Runtime source cases. Composite export-only mappings must assert the standard emitted node sequence, ORT execution, eager TorchSharp parity, and a diagnostic when reverse generation is requested.
- Current ONNXScript source: `third_party/onnxscript/tests/function_libs/torch_lib/ops_test_data.py`, cases named in the family tests and inventory above. Runtime sources: `third_party/onnxruntime/onnxruntime/test/providers/cpu/math/element_wise_ops_test.cc`, `third_party/onnxruntime/onnxruntime/test/providers/cpu/tensor/where_op_test.cc`, `third_party/onnxruntime/onnxruntime/test/providers/cpu/tensor/isinf_test.cc`, `third_party/onnxruntime/onnxruntime/test/providers/cpu/tensor/cast_op_test.cc`, and `third_party/onnxruntime/onnxruntime/test/providers/cpu/activation/activation_op_test.cc`.

## Acceptance Criteria

- Every operator in the declared family has paired directional coverage or an explicitly tested one-way capability.
- Broadcast/type limitations and unsupported overload diagnostics are recorded alongside the tests.
- OXY-033 is limited to reductions and selection that is not pointwise; OXY-027 depends on this task and OXY-030—OXY-033.
