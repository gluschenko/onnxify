## Summary

Migrate the syntax that makes model-shaped code practical: arrays, collection expressions, tuples, shape/dtype metadata reads, and static control-flow constructs.

This task builds on the basic data-flow migration from `OXY-004` and still avoids helper method and module recursion work, which belongs in `OXY-006`.

## Depends On

- `OXY-001`: metadata and shape/type resolver
- `OXY-002`: scanner and IR skeleton
- `OXY-003`: printer skeleton
- `OXY-004`: basic data-flow migration

## Enables

- `OXY-006`: helper methods and module calls
- `OXY-007`: Torch operation families that require shape arrays

## Goals

- Migrate array and collection syntax used by current deep export tests.
- Migrate tuple output and deconstruction support.
- Migrate shape and dtype metadata reads.
- Migrate static conditionals and no-op scope constructs.
- Keep runtime shape resolution centralized in the `OXY-001` resolver.

## Non-Goals

- Do not migrate local helper method invocation.
- Do not migrate recursive user module export.
- Do not implement ONNX dynamic control flow.
- Do not migrate broad Torch op families unless needed as tiny fixtures for this syntax.

## Scope

Migrate:

- array expressions
- collection expressions
- explicit `new long[]` / implicit arrays / sized array initializer shapes
- decompiler inline-array artifacts
- tuple expressions and tuple outputs
- deconstruction statements
- `x.shape[i]`
- `x.dtype`
- `x.device`
- static conditional expressions
- static `if` branches
- null-guarded conditionals where current behavior supports static resolution
- validation guard calls that should be ignored
- `using` scopes that only express disposal/no-grad guard behavior
- static `foreach` over statically known module collections, without recursive child module export

## Required IR Additions

Implement end-to-end:

- `ArrayExpressionNode`
- `InlineArrayExpressionNode`
- `TupleExpressionNode`
- `DeconstructionNode`
- `IndexerExpressionNode`
- `ShapeDimensionNode` or equivalent semantic node
- `SymbolicTensorMemberNode`
- `ConditionalExpressionNode`
- `IfNode`
- `UsingScopeNode`
- `ForeachNode`
- `IgnoredValidationCallNode`

## Shape And Type Rules

- Symbolic dimensions from `TensorDimension` must stay symbolic unless a consumer explicitly requires a fixed value.
- Runtime-known dimensions should come from the metadata resolver.
- Shape arrays for `view`/`reshape` must preserve ONNX semantics such as copy-dimension sentinels where current behavior relies on them.
- Dtype reads should not force runtime tensor materialization unless the existing exporter already requires it.
- Conflicting shape facts must produce diagnostics, not silent guesses.

## Tests

Add focused tests for:

- inline array shape resolution
- explicit `new long[]` shape resolution
- assigned local shape array
- collection expression tensor list
- tuple return with multiple outputs
- tuple deconstruction
- `x.shape[i]`
- `x.dtype` used in factory calls
- static bool branch selection
- static null branch selection
- validation statement ignored
- no-grad using statement ignored
- static foreach over known collection
- unsupported dynamic branch diagnostic

Validation requirements:

- graph structure assertions
- initializer value assertions for shape arrays
- ONNX Runtime session creation where executable
- eager vs runtime parity where deterministic

## Acceptance Criteria

- Existing shape/array/tuple/control-flow tests use the new scanner/printer path.
- Shape and dtype resolution is centralized through the metadata/resolver layer.
- No ONNX dynamic control-flow nodes are introduced accidentally.
- Unsupported dynamic control flow produces clear diagnostics or falls back until fallback removal.
- The old monolithic helpers for migrated constructs are removed when no longer used.

## Risks

- Decompiler inline-array syntax is fragile. Keep test fixtures close to actual decompiled forms.
- Static branch selection can accidentally evaluate code with side effects. Only evaluate safe metadata/constants.
