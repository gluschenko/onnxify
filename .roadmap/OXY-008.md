## Summary

Finalize the user-extensible deep export API and remove the monolithic fallback after migrated coverage is sufficient.

This task turns the internal architecture from `OXY-001` through `OXY-007` into a maintainable public surface for library consumers.

## Depends On

- `OXY-001`: metadata foundation
- `OXY-002`: scanner and IR skeleton
- `OXY-003`: printer skeleton
- `OXY-004`: basic data-flow migration
- `OXY-005`: shapes, arrays, tuples, and static control flow
- `OXY-006`: helpers and modules
- `OXY-007`: Torch operation families

## Goals

- Expose a small stable public extension API.
- Let users register custom metadata providers, module exporters, method lowerings, scanners, and printers.
- Provide deterministic extension ordering.
- Provide diagnostics for extension failures and ambiguous matches.
- Remove the old monolithic fallback when parity is sufficient.
- Document the public API for package users.

## Non-Goals

- Do not expose every internal IR node publicly.
- Do not make ICSharpCode.Decompiler a required public dependency unless explicitly accepted.
- Do not promise binary stability for experimental extension points.
- Do not add a plugin system beyond normal .NET object registration.

## Public Configuration Surface

Add public options without breaking existing overloads.

Suggested shape:

```csharp
public sealed class TorchDeepExportOptions
{
    public DeepExportExtensionCollection Extensions { get; }

    public DeepExportDiagnosticLevel DiagnosticLevel { get; set; }

    public bool IncludeDebugIr { get; set; }

    public bool EnableRuntimeMetadataReflection { get; set; }
}
```

Add new overloads where needed:

```csharp
module.ExportOnnxModel(
    input,
    output,
    modelOptions,
    deepExportOptions
);
```

Existing overloads must keep current behavior.

## Extension Registration

Support fluent registration:

```csharp
var exportOptions = new TorchDeepExportOptions()
    .AddMetadataProvider(new MyModelMetadataProvider())
    .AddModuleExporter<MyCustomBlock>(new MyCustomBlockExporter())
    .AddMethodLowering(typeof(MyOps).GetMethod(nameof(MyOps.Swish))!, new SwishLowering())
    .AddScanner(new MyScanner())
    .AddPrinter(new MyPrinter());
```

Required extension kinds:

- metadata provider
- module exporter
- method/helper lowering
- Torch operation lowering by symbolic name
- scanner
- printer
- graph post-processor
- diagnostic listener

## Public Interfaces

Design stable public interfaces with narrow contexts:

```csharp
public interface IDeepExportMetadataProvider
{
    void Collect(
        DeepExportMetadataContext context,
        object module,
        DeepExportModuleMetadataBuilder metadata
    );
}

public interface IDeepExportModuleExporter
{
    bool CanExport(DeepExportModuleExportContext context, object module);

    DeepExportValue Export(
        DeepExportModuleExportContext context,
        object module,
        IReadOnlyList<DeepExportValue> inputs
    );
}

public interface IDeepExportScanner
{
    bool CanScan(DeepExportScanContext context, DeepExportSyntax syntax);

    DeepExportNode Scan(
        DeepExportScanContext context,
        DeepExportSyntax syntax
    );
}

public interface IDeepExportPrinter
{
    bool CanPrint(DeepExportPrintContext context, DeepExportNode node);

    DeepExportValue Print(
        DeepExportPrintContext context,
        DeepExportNode node
    );
}
```

If raw ICSharpCode.Decompiler AST access is needed, prefer wrapping it in `DeepExportSyntax` first. Direct raw access should be marked experimental if exposed.

## Extension Ordering

Add deterministic priority:

```csharp
public enum DeepExportExtensionPriority
{
    BeforeBuiltIns,
    Normal,
    AfterBuiltIns,
}
```

Rules:

- built-in exact matches normally beat generic built-ins
- user extensions can intentionally override built-ins with `BeforeBuiltIns`
- user extensions can fill gaps with `AfterBuiltIns`
- ambiguous equal-priority matches produce diagnostics

## Attribute-Based Registration

Consider optional attributes:

```csharp
[DeepExportModuleExporter(typeof(MyCustomBlockExporter))]
public sealed class MyCustomBlock : torch.nn.Module<torch.Tensor, torch.Tensor>
{
}

[DeepExportMethodExporter(typeof(SwishExporter))]
public static torch.Tensor Swish(torch.Tensor input)
{
    return input * torch.sigmoid(input);
}

[DeepExportMetadataProvider(typeof(MyModelMetadataProvider))]
public sealed class MyModel : torch.nn.Module<torch.Tensor, torch.Tensor>
{
}
```

Explicit options-based registration must remain available for third-party types that cannot be annotated.

## Diagnostics

Public diagnostics must identify:

- stage: metadata, scan, print, post-process
- module type
- method name when available
- syntax or IR node when available
- extension type
- extension priority
- whether the extension declined, failed, or returned an invalid value
- inner exception for extension failures

Support:

- strict mode: extension exceptions fail export
- permissive mode: extension exceptions become diagnostics and dispatch continues when safe

## Cleanup

After extension APIs are tested and migrated coverage is sufficient:

- remove the old monolithic AST fallback
- keep `TorchModuleExportExtensions` as public facade and orchestration
- delete dead private helpers
- ensure new feature work lands in scanner/printer/metadata/module-exporter components
- update internal skill docs if contributor workflow changes

## Tests

Add tests for:

- external-style project can compile against public extension APIs
- custom metadata provider contributes dimensions
- custom module exporter emits graph
- custom helper method lowering emits graph
- extension priority override
- ambiguous extensions produce diagnostics
- extension exception behavior in strict mode
- extension exception behavior in permissive mode
- public overloads remain source-compatible

## Acceptance Criteria

- Users can extend deep export without forking `Onnxify.TorchSharp`.
- Existing public export overloads remain compatible.
- At least one custom metadata provider, module exporter, and method lowering are covered by tests.
- Diagnostics identify failing extensions clearly.
- The old monolithic fallback is removed or explicitly deprecated with no active feature work directed there.
- Package docs and release notes describe the extension surface.

## Risks

- Public APIs are hard to change after release. Keep the stable surface small.
- Exposing raw decompiler AST types can pin Onnxify to ICSharpCode.Decompiler compatibility details.
- Too many extension hooks can make export behavior unpredictable. Priorities and diagnostics must be deterministic.
