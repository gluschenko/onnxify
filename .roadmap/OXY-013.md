## Summary

Add integration tests that validate NuGet packages before publishing.

The repository already has project-level tests, but packaging can still fail in ways that normal project references do not catch: missing files, wrong package metadata, broken package readmes, missing transitive dependencies, incompatible target frameworks, generated assets not included, or public examples that only work from source. This task should create a pre-publish validation path that packs the packages and consumes them from a local NuGet feed in clean test projects.

## Depends On

- Existing NuGet packaging configuration in `src/Directory.Build.props` and package `*.csproj` files.
- Existing `.docs/nuget` README and release-notes layout.
- Current solution build and test workflow.
- Published package list and package dependency relationships.

## Enables

- Higher confidence before pushing packages to NuGet.org.
- Detection of package-only regressions that project-reference tests miss.
- A repeatable local and CI-friendly pre-publish gate.
- Safer validation of generated package docs, package metadata, dependencies, and consumer experience.

## Goals

- Define the package set that must be validated before publishing.
- Add a repeatable test workflow that runs `dotnet pack`, creates a local package source, and restores packages into clean consumer projects.
- Validate package metadata, readme inclusion, license metadata, repository metadata, icons if used, and package dependency versions.
- Compile and run minimal consumer smoke tests for each published package.
- Include integration coverage for package combinations where one Onnxify package consumes another.
- Make the workflow suitable for CI and local execution without requiring NuGet.org credentials.
- Document how maintainers should run the pre-publish validation before release.

## Non-Goals

- Do not publish packages as part of the integration tests.
- Do not require live NuGet.org access except for ordinary dependency restore.
- Do not replace unit tests or package-specific feature tests.
- Do not make release signing, provenance, or NuGet.org API-key management part of this task unless the existing pipeline already owns it.
- Do not validate every large model or long-running example in the package smoke tests.

## Validation Shape

Prefer a clean, local-package workflow:

1. Build and pack all publishable packages into a temporary local feed.
2. Create fresh consumer projects outside the source project graph.
3. Add packages from the local feed using exact versions produced by the pack step.
4. Restore, build, and run focused smoke tests.
5. Fail on package warnings that should block publishing.

The consumer projects should use package references, not project references, so missing packed assets or metadata issues are visible.

## Implementation Steps

1. Inventory publishable projects and package relationships.
2. Decide whether the integration tests live in `src/Onnxify.Tests`, a separate test project, or a release-validation script with test assertions.
3. Add a deterministic pack output directory and local NuGet source setup for tests.
4. Add package metadata assertions for all publishable packages.
5. Add minimal consumer smoke tests for each package:
   - core `Onnxify`
   - `Onnxify.TorchSharp`
   - `Onnxify.Safetensors`
   - `Onnxify.HuggingFace`
   - `Onnxify.ProjectGenerator`
   - `Onnxify.ModelGenerator`
   - any `Onnxify.ML` packages that are publishable
   - `Onnxify.CLI` if distributed as a NuGet tool or package
6. Add package-combination tests where cross-package dependencies matter.
7. Ensure temporary feeds, generated projects, and package caches are isolated and cleaned up.
8. Add CI wiring or documented CI command once the local workflow is stable.
9. Update release documentation to require the integration test gate before publishing.

## Tests

The new validation should cover:

- packages can be packed successfully in release configuration
- all expected package files are present
- package metadata matches repository conventions
- NuGet readmes are included and renderable as package readmes
- clean consumer projects restore from the local feed
- clean consumer projects build without project references
- representative package APIs execute successfully from installed packages
- package dependency versions are exact or ranged according to repository policy
- package warnings that indicate publish risk fail the validation

## Acceptance Criteria

- A maintainer can run one documented command to pack packages and run local-feed integration tests before publishing.
- The validation consumes the produced packages through package references, not project references.
- Each publishable Onnxify package has at least one focused consumer smoke test or an explicit documented reason it is excluded.
- Package metadata and readme inclusion are checked before publishing.
- The workflow can run in CI without NuGet.org publish credentials.
- Release documentation explains when and how to run the pre-publish integration tests.

## Risks

- Integration tests that pack and restore packages can be slower than unit tests. Keep them separated or clearly filterable.
- Local NuGet cache behavior can hide package issues unless versions, feeds, and caches are isolated.
- Network restore can make CI flaky if external feeds are unavailable. Prefer normal restore caching and avoid live package publishing.
- Multi-targeted packages may pass for one target framework while failing for another. Include the target frameworks that matter for supported consumers.
