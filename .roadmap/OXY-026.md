## Summary

Make existing public APIs delegate to `Onnxify.Compiler` and expose a narrow, stable extension surface for compiler consumers.

## Depends On

- [OXY-020](OXY-020.md).
- [OXY-023](OXY-023.md).
- [OXY-024](OXY-024.md).

## Goals

- Keep existing ModelGenerator and TorchSharp public overloads source-compatible.
- Add compiler-backed options for diagnostics, intermediate-representation inspection, runtime metadata reflection, and extension collections where appropriate.
- Support narrow custom metadata providers, module exporters, scanners, printers, and method lowerings.
- Define deterministic extension priority and strict/permissive failure behavior.
- Deprecate or remove old direction-specific registries only after equivalent compiler mappings exist.

## Tests

- Existing public APIs delegate to compiler services.
- External-style consumer compiles against the extension surface.
- Custom providers, exporters, scanners, printers, priority overrides, ambiguity, and strict/permissive exceptions are covered.

## Verification

- A consumer-style test calls existing public overloads and observes compiler-backed behavior.
- Extension tests prove deterministic priority, ambiguity diagnostics, and strict/permissive exception behavior.
- A compatibility audit identifies each remaining old registry/path and its retirement condition.

## Acceptance Criteria

- No new feature work is directed to the old monolithic path.
- Compatibility façades and extension points are documented and tested.

## Worklog

- 2026-09-05: Created as phase seven of OXY-019.
- 2026-10-07: Added compiler options, priority-ordered extension contracts, callbacks, strict/permissive handling, and runtime reflection control while preserving existing entry points. Existing whole-model TorchSharp export now tries the compiler when mappings and declared tensor contracts match, then retains the legacy exporter for unsupported syntax, state, mappings, or mismatched contracts. `TorchModuleExperimental` generates through the compiler; legacy `TorchModule` continues through its existing printer. Added consumer-facing tests, ONNX Runtime parity, docs, and analyzer packaging for the compiler dependency.
- Compatibility audit: `ExportOnnxModel(...)` uses compiler output only for fully covered trees with matching tensor names/types/shapes; all other cases use the existing exporter. Direct `TorchModule.Export(graph, input)` module/operator exporters remain the compatibility path for stateful module semantics. ModelGenerator `TorchModule` remains on `TorchModulePrinter`; `TorchModuleExperimental` is opt-in, mapping-limited, and reports unsupported operators as `OMG006` without fallback. Remove those compatibility paths only when equivalent mappings and parity tests cover their module/state behavior.
- Verification: compiler build and 70 tests passed on net8.0 and net10.0. Focused `Onnxify.Tests` passed for experimental ReLU generation/compilation/runtime parity, unsupported compiler operation diagnostics, mode conflict, compiler-backed TorchSharp ReLU export, and 49 legacy deep-export tests.
