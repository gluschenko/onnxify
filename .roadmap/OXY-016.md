## Summary

Add `chat_template.jinja` support to `Onnxify.ModelGenerator` so generated model wrappers can serialize high-level chat context objects into the flat prompt text expected by tokenizer chat templates, and parse compatible rendered prompt text back into high-level chat context objects.

The feature should target Hugging Face Transformers chat templates first. Transformers stores chat templates as Jinja in a tokenizer `chat_template` attribute or `chat_template.jinja` file, and templates commonly consume `messages`, `add_generation_prompt`, tokenizer special tokens, optional `tools`, tool calls, tool responses, and multimodal content placeholders.

Initial support should focus on a practical, deterministic Jinja profile that covers common instruction-tuned ONNX model repositories without attempting to implement every possible Python/Jinja behavior.

Reference material:

- https://huggingface.co/docs/transformers/en/chat_templating_writing
- https://huggingface.co/onnx-community/gemma-4-E4B-it-ONNX/blob/main/chat_template.jinja
- https://github.com/pallets/jinja
- https://github.com/huggingface/huggingface.js/tree/main/packages/jinja

## Source Findings

The Hugging Face JavaScript package under `packages/jinja/src` is the closest implementation reference for this task.

Important implementation details to preserve or deliberately diverge from:

- `index.ts` exposes a deliberately small public API: `Template`, `Template.render(...)`, `Template.format(...)`, and lower-level `Environment`, `Interpreter`, `tokenize`, and `parse`.
- `Template` tokenizes with `lstrip_blocks: true` and `trim_blocks: true`, matching the chat-template usage profile more closely than default Jinja settings.
- `lexer.ts` implements text tokens, statement tags, expression tags, comments, whitespace trimming via `{%-`, `-%}`, `{{-`, and `-}}`, escaped string characters, and a Transformers-specific `{% generation %}` / `{% endgeneration %}` tag removal pass.
- `ast.ts` includes `Program`, `If`, `For`, `Break`, `Continue`, `SetStatement`, `Macro`, `CallStatement`, `FilterStatement`, comments, literals, member access, calls, filters, tests, slices, keyword arguments, spread arguments, tuple/object/array literals, select expressions, and ternary expressions.
- `parser.ts` supports the expression grammar needed by real chat templates, including Python-like `and`, `or`, `not`, `in`, `not in`, `is`, attribute/index access, slicing, tuple unpacking, keyword arguments, and filter chains.
- `runtime.ts` uses explicit runtime value types and Jinja/Python-like truthiness rather than native JavaScript truthiness.
- `runtime.ts` includes string methods and filters such as `upper`, `lower`, `strip`, `trim`, `title`, `capitalize`, `rstrip`, `lstrip`, `startswith`, `endswith`, `split`, `replace`, `tojson`, `indent`, `join`, `int`, `float`, `default`, `sort`, `selectattr`, `rejectattr`, `map(attribute=...)`, `items`, `dictsort`, `safe`, `list`, `first`, `last`, `reverse`, `string`, and `unique`.
- `runtime.ts` includes tests such as `boolean`, `callable`, `odd`, `even`, `false`, `true`, `none`, `string`, `number`, `integer`, `iterable`, `mapping`, `sequence`, `lower`, `upper`, `defined`, `undefined`, `equalto`, and `eq`.
- `runtime.ts` includes globals `true`, `false`, `none`, title-case aliases, `raise_exception`, `range`, `strftime_now`, and `namespace`.
- `format.ts` can roundtrip parsed templates through a normalized formatting pass and should be ported only if useful for diagnostics, reversible-template analysis, or tests.
- The package tests include a large corpus of real chat templates and focused lexer/parser/runtime tests. A C# port should treat that corpus as compatibility guidance.

- Existing `Onnxify.ModelGenerator` generated wrapper architecture.

- A tokenizer/config discovery path that can locate `chat_template.jinja` or tokenizer metadata containing `chat_template`.

- A stable set of chat context model types for messages, roles, content parts, tool definitions, tool calls, and tool responses.
- A decision on where shared runtime types live so generated wrappers can depend on them without duplicating the Jinja engine into every generated project.

## Enables

- Generated ONNX model wrappers that can accept rich chat objects instead of only raw prompt strings.
- Roundtrip prompt inspection and editing workflows for chat logs.
- Better compatibility with Hugging Face ONNX chat model repositories that publish tokenizer chat templates.
- Future higher-level APIs for tool calling, multimodal placeholder prompts, and chat session persistence.

## Goals

- Define public chat context object models for:
  - messages with `system`, `user`, `assistant`, and `tool` roles
  - plain text content
  - multimodal content placeholders such as image or video markers
  - assistant tool calls
  - tool responses
  - optional generation prompt state
  - optional tool definitions
- Load chat templates from local model directories and generated-project inputs.
- Render supported Jinja chat templates into exact flat prompt text, preserving model-specific whitespace and special tokens.
- Parse compatible rendered prompt text back into chat context objects where the template structure is sufficiently reversible.
- Detect non-reversible templates and report clear diagnostics instead of returning misleading objects.
- Support tokenizer special tokens such as `bos_token`, `eos_token`, and other entries from a special-token map.
- Support the Hugging Face conventions around `messages`, `add_generation_prompt`, `tools`, `tool_calls`, and tool responses.
- Add generated wrapper APIs that keep raw string prompting available while making chat-object prompting ergonomic.
- Port or reimplement enough of the Hugging Face JavaScript Jinja engine to pass a representative compatibility corpus in C#.
- Keep the forward renderer deterministic, culture-aware only where explicitly configured, and free from arbitrary .NET reflection or host code execution.
- Document the supported Jinja profile, reversibility rules, and known limitations.

## Non-Goals

- Do not implement the full Python Jinja runtime if a limited profile covers the target chat templates.
- Do not infer high-level chat objects from arbitrary natural language prompts that were not produced by a supported template.
- Do not tokenize or detokenize text in this task unless existing tokenizer support is already available and required for validation.
- Do not require network access at runtime to render or parse templates.
- Do not silently drop unsupported content parts, tools, or template branches.
- Do not couple chat-template support to a single model family such as Gemma.
- Do not support Jinja template inheritance, includes, imports, loaders, HTML autoescaping, sandbox policy APIs, async rendering, or arbitrary host object method invocation in the first implementation.
- Do not generate a separate copy of the Jinja runtime into every model wrapper unless packaging constraints make a shared runtime impossible.
- Do not make reverse parsing a blocking requirement for the first forward-rendering milestone.

## Design Questions

- Should `Onnxify.ModelGenerator` generate chat serializer code directly, depend on a shared runtime serializer package surface, or both?
- Which .NET Jinja engine, if any, should be used, and does it preserve Hugging Face-compatible whitespace control closely enough?
- Should a C# implementation be ported from the Hugging Face JavaScript Jinja package rather than from full upstream Python Jinja?
- Should reverse parsing be template-AST based, generated from the template, or implemented through model-specific reversible pattern descriptors?
- How should the API communicate partial reversibility, unsupported branches, and ambiguous parses?
- Should chat context types live in `Onnxify.ModelGenerator`, a shared runtime project, or a new package-facing namespace?
- How should tool definitions be represented: raw JSON schema, typed helper models, or both?
- How should multimodal content be represented before the repository has first-class image/video preprocessing?
- Should `strftime_now` use the system clock, an injectable clock, or be disabled unless explicitly enabled to keep tests deterministic?
- Should unknown variables render as empty strings, propagate `Undefined`, or fail in strict mode?
- Should CLR objects be converted through reflection, dictionaries, source-generated adapters, or explicit `IChatTemplateValue` models?

## C# API Specification

The implementation should expose a low-level Jinja API that is usable without generated model wrappers:

```csharp
var template = JinjaTemplate.Parse(
    templateText,
    new JinjaTemplateOptions
    {
        TrimBlocks = true,
        LStripBlocks = true,
        EnableTransformersGenerationTags = true,
        StrictUndefined = false
    }
);

var result = template.Render(
    new JinjaRenderContext()
        .Set("messages", messages)
        .Set("bos_token", "<s>")
        .Set("eos_token", "</s>")
        .Set("add_generation_prompt", true)
);
```

Suggested low-level types:

- `JinjaTemplate`: parsed reusable template with `Parse`, `TryParse`, `Render`, `TryRender`, and optional `Format`.
- `JinjaTemplateOptions`: preprocessing and runtime settings such as `TrimBlocks`, `LStripBlocks`, `KeepTrailingNewline`, `EnableTransformersGenerationTags`, `StrictUndefined`, and optional `IClock`.
- `JinjaRenderContext`: explicit variable bag that converts .NET values into runtime values.
- `JinjaRuntimeValue`: base representation for string, integer, float, boolean, object, array, tuple, function, null, and undefined values.
- `JinjaTemplateDiagnostic`: structured diagnostics with severity, message, source span when available, and node/token context.
- `JinjaTemplateException`: base exception for parse, render, unsupported-feature, and `raise_exception` failures.
- `IJinjaFilter`, `IJinjaTest`, and `IJinjaFunction`: extension points for filters, tests, and callable globals.

The chat-template layer should sit above the Jinja API:

```csharp
var chatTemplate = ChatTemplateSerializer.FromJinja(
    templateText,
    new ChatTemplateOptions
    {
        SpecialTokens = specialTokens,
        Tools = tools,
        AddGenerationPrompt = true
    }
);

var prompt = chatTemplate.Serialize(chatContext);
var parseResult = chatTemplate.TryDeserialize(prompt);
```

Suggested chat-template types:

- `ChatTemplateSerializer`: owns a parsed `JinjaTemplate`, tokenizer special tokens, and chat-template policy.
- `ChatTemplateOptions`: `SpecialTokens`, `AddGenerationPrompt`, optional `Tools`, reversible parsing policy, unknown-role policy, and diagnostics mode.
- `ChatContext`: ordered message list plus optional template variables.
- `ChatMessage`: role, content parts, optional name, tool calls, tool-call id, and metadata.
- `ChatRole`: `System`, `User`, `Assistant`, `Tool`, plus an extensible string-backed fallback for model-specific roles.
- `ChatContentPart`: text content plus future image/video/audio placeholders without requiring preprocessing in this task.
- `ChatToolDefinition`: raw JSON schema first, with typed helper builders as a later convenience.
- `ChatToolCall`: id, name, arguments as JSON or structured object.
- `ChatTemplateParseResult`: success flag, parsed `ChatContext`, diagnostics, and reversibility confidence.

Generated wrappers should expose this as a convenience surface while preserving raw prompt APIs:

```csharp
var prompt = model.ChatTemplate.Serialize(chatContext);
var output = await model.RunAsync(prompt);

var output = await model.RunChatAsync(
    chatContext,
    new ChatRunOptions { AddGenerationPrompt = true }
);
```

Generated wrappers must not require chat-template support when no template is available.

## Supported Engine Scope

Port the Hugging Face JavaScript Jinja subset before inventing new behavior.

The first C# engine milestone should cover:

- tokenization and preprocessing, including trailing newline trimming, `trim_blocks`, `lstrip_blocks`, whitespace-control markers, comments, escaped strings, and Transformers `generation` tags
- AST node coverage equivalent to the JavaScript package
- expression grammar for arithmetic, string concatenation with `+` and `~`, comparisons, membership, boolean operators, unary `not`, filters, tests, calls, member/index access, slices, arrays, tuples, objects, ternaries, keyword arguments, and spread arguments
- statements for `if`, `elif`, `else`, `for`, `else` in loops, `set`, block `set`, `macro`, `call`, `filter`, `break`, `continue`, and comments
- runtime values with Jinja/Python-like truthiness
- globals, filters, tests, and string/object/array methods listed in Source Findings
- loop metadata: `loop.index`, `loop.index0`, `loop.revindex`, `loop.revindex0`, `loop.first`, `loop.last`, `loop.length`, `loop.previtem`, and `loop.nextitem`
- deterministic JSON output for `tojson`, including `indent`, `ensure_ascii`, `sort_keys`, and `separators`
- structured errors for unknown statements, unsupported filters/tests, invalid calls, undefined operations, and `raise_exception`

Explicit first-milestone exclusions:

- Jinja inheritance, include/import/from, loaders, blocks, super calls, template files beyond the selected chat template, autoescaping, i18n, async, streaming, sandbox policy APIs, custom delimiters, and arbitrary .NET method invocation
- exact compatibility with every Pallets Jinja edge case outside the Hugging Face chat-template subset
- reverse parsing for templates that mutate content, branch on text content, use arbitrary macros, or do not emit stable role/content delimiters

## Extension Points

Design the runtime so future work can add behavior without rewriting the parser:

- `IJinjaFilterRegistry` for model-specific or future Hugging Face filters.
- `IJinjaTestRegistry` for additional `is ...` tests.
- `IJinjaFunctionRegistry` for globals such as `strftime_now` and controlled future helpers.
- `IJinjaValueConverter` for converting CLR objects, dictionaries, JSON documents, generated chat types, and future tokenizer metadata.
- `IChatTemplateVariableProvider` for adding tokenizer/config variables beyond `messages`, special tokens, tools, and `add_generation_prompt`.
- `IChatTemplateReversibilityAnalyzer` for classifying templates as reversible, partially reversible, or render-only.
- `IChatTemplatePromptParser` for model-family-specific reverse parsing when generic AST analysis cannot prove reversibility.
- `IChatContentPartRenderer` for future multimodal content placeholders.
- `IChatToolSchemaFormatter` for future typed tool schema generation.
- `IClock` or equivalent time provider for deterministic `strftime_now`.

## Acceptance Criteria

- `Onnxify.ModelGenerator` can include chat-template support in generated wrappers when a supported template is present.
- A low-level reusable C# Jinja renderer exists and is tested independently from generated wrappers.
- The C# renderer passes the selected Hugging Face JavaScript Jinja compatibility corpus or documents every intentional deviation.
- High-level chat context objects can be serialized into the exact flat prompt format for supported Jinja templates.
- Compatible rendered prompt text can be parsed back into high-level chat context objects.
- Unsupported or non-reversible template features produce clear diagnostics.
- The implementation covers common Hugging Face variables and conventions for `messages`, `add_generation_prompt`, special tokens, `tools`, `tool_calls`, and tool responses.
- Focused tests cover forward rendering, reverse parsing, generated-wrapper integration, and failure diagnostics.
- Public docs or NuGet notes describe the feature, supported profile, and limitations.
- Extension points for filters, tests, functions, value conversion, content-part rendering, tool-schema formatting, and reversible parsing exist without exposing arbitrary host execution.

## Risks

- Reverse parsing from arbitrary template output can be ambiguous. Keep reversibility explicit and testable.
- Jinja compatibility across implementations can differ, especially around whitespace trimming, filters, Python-style methods, and direct object rendering.
- Tool-calling templates can be large and model-specific; the first implementation should avoid claiming universal support.
- Multimodal templates may emit placeholder tokens that require later processor expansion outside this task.
- Public chat object models may become a long-lived API surface. Keep the first shape small but extensible.
- Porting the JavaScript runtime directly can import JavaScript-specific equality, number, Unicode, and culture behavior. Validate C# behavior against golden outputs rather than assuming line-by-line parity.
- Letting templates call arbitrary CLR methods would create security and determinism problems. Keep method access limited to explicit runtime builtins and registries.
- `strftime_now` can make tests and generated outputs nondeterministic unless the clock is injectable.
- The low-level Jinja runtime may be valuable outside `ModelGenerator`; avoid burying reusable code in generated output.
