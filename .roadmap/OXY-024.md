## Summary

Move operator semantics into the compiler-owned registry and migrate an initial useful set of operators through both directions.

## Depends On

- [OXY-021](OXY-021.md).
- [OXY-022](OXY-022.md).
- [OXY-023](OXY-023.md).

## Goals

- Define one mapping contract for parse/import and print/export behavior.
- Classify every mapping as bidirectional, export-only, import-only, or unsupported.
- Start with basic arithmetic, ReLU/activations, matmul, shape operations, factories, selection, reductions, casts, and other already-covered operations as capacity allows.
- Keep operation-specific lowering out of `TorchModuleExportExtensions.cs` and ModelGenerator registries as migration proceeds.
- Require every new operator to have verification from `ONNX -> TorchSharp` and `TorchSharp -> ONNX`.

## Tests

- Each migrated operator has structural graph assertions in both directions.
- ONNX Runtime session creation is tested where the emitted graph is executable.
- Deterministic fixtures compare TorchSharp eager output with ONNX Runtime output.
- Unsupported overloads produce explicit diagnostics instead of silently generating invalid code.

## Acceptance Criteria

- At least one operator is implemented through one shared bidirectional mapping.
- Adding an operator requires paired directional verification or an explicit tested one-way classification.
