## Summary

Migrate deep export behavior that crosses method and module boundaries.

This task covers local helper methods, generated helper methods, known TorchSharp module calls, sequential traversal, and recursive user module export.

## Depends On

- `OXY-001`: metadata foundation
- `OXY-002`: scanner and IR skeleton
- `OXY-003`: printer skeleton
- `OXY-004`: basic data flow
- `OXY-005`: shapes, arrays, tuples, and static control flow

## Enables

- `OXY-007`: Torch operation families used inside helper/module bodies
- `OXY-008`: public module exporter API

## Goals

- Migrate local helper method invocation.
- Migrate helper parameter binding and return handling.
- Migrate generated helper method recognition.
- Migrate known TorchSharp module `forward` calls.
- Migrate recursive user module export.
- Keep direct module exporters in `TorchModuleExtensions` reusable.

## Non-Goals

- Do not migrate every Torch operation family.
- Do not expose the final public module exporter API.
- Do not support arbitrary side-effecting helper methods.
- Do not implement dynamic dispatch beyond current deep export behavior.

## Scope

Migrate:

- local helper invocation
- helper method decompilation reuse
- helper method scan cache
- helper method parameter binding
- helper method return values
- tuple-returning helper methods
- generated graph helper detection
- generated split/slice helper lowerings currently supported
- known module `forward` calls
- direct module exporter bridge to `TorchModuleExtensions.Export(...)`
- sequential module traversal
- recursive user module export when no concrete exporter exists
- unsupported non-validation void helper diagnostics

## Required IR Additions

Implement end to end:

- `LocalHelperInvocationNode`
- `GeneratedHelperInvocationNode`
- `ModuleForwardInvocationNode`
- `KnownModuleExportNode` or equivalent semantic node
- `RecursiveModuleExportNode` or equivalent semantic node
- helper method declaration/cache model
- helper call frame/scope model

## Scope Rules

- Helper calls must create child scopes.
- Parameter names in helper methods must bind to caller argument values.
- Return values must flow back as `DeepExportValue`.
- Tuple and array values must preserve item ordering.
- Recursive module export must use the child module's metadata context.
- Diagnostics must include both caller and callee method names when possible.

## Tests

Add focused tests for:

- local helper projection
- helper method with scalar arguments
- helper method returning tuple
- deconstruction of helper tuple output
- generated slice helper
- generated split helper
- known module forward call
- sequential module chain
- recursive user child module
- unsupported void helper throws clear diagnostic
- helper diagnostics include method names

Validation requirements:

- graph structure assertions
- initializer assertions for helper-emitted constants
- ONNX Runtime session creation
- TorchSharp eager vs ONNX Runtime parity for deterministic fixtures
- deep import/export parity tests when generated helper behavior touches roundtrip paths

## Acceptance Criteria

- Current helper/module deep export tests run through scanner/printer components.
- Helper scopes no longer rely on the old monolithic method interpreter.
- Known module exports still delegate to `TorchModuleExtensions` where appropriate.
- Recursive user module export works through the new pipeline.
- Unsupported helper forms fail with clear diagnostics.

## Risks

- Recursive module export can create confusing cycles. Detect and diagnose cycles.
- Helper scopes can accidentally leak locals between methods. Keep scope tests explicit.
- Generated helper syntax may change. Keep recognition semantic rather than string-only where practical.
