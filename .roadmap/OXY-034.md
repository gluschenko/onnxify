## Summary

Refactor the operator implementation in `Onnxify.Compiler`: replace the growing `CompilerOperatorMapping` configuration, operator-name dispatch branches, and semantics scattered across frontends and backends with an internal polymorphic operator model. Preserve existing behavior and public APIs.

## Goals

- Introduce an internal abstract operator base class under `Onnxify.Compiler/Operators` with contracts for scanning ONNX nodes and TorchSharp calls, and for generating ONNX and TorchSharp output.
- Move access to the computation tree, source spans, graph, and diagnostics into phase contexts so operator classes define semantics without owning compiler orchestration.
- Remove `CompilerOperatorMapping` and replace it with a registry of operator instances indexed by ONNX domain/name and supported TorchSharp forms. Detect duplicate registrations when building the registry.
- Add reusable base classes for shared families, including unary, binary, and arithmetic operators; represent concrete operations as dedicated subclasses.
- Move operator-specific recognition, validation, and generation into operator classes, removing operator-name/family dispatch from central compiler files.
- Keep syntax checks, control-flow handling, orchestration, and general diagnostic processing in their respective compiler phases; do not force them into operator classes.
- Keep the base class and registry internal. Do not change supported mapping semantics, public APIs, or façade behavior.

## Design Sketch

The operator abstraction should own operation-specific recognition, normalization, validation, and output semantics. Compiler phases should own traversal, shared IR state, diagnostics collection, and source/graph bookkeeping. The following C# is an architectural sketch; exact internal context and result types can be refined during implementation.

```csharp
internal abstract class CompilerOperator
{
    public abstract CompilerOperatorIdentity Identity { get; }

    public abstract IReadOnlyCollection<CompilerTorchSharpForm> TorchSharpForms { get; }

    public abstract CompilerOperationCapability Capability { get; }

    public abstract CompilerResult<CompilerOperation> ScanOnnx(
        OnnxNode node,
        OnnxOperatorScanContext context);

    public abstract CompilerResult<CompilerOperation> ScanTorchSharp(
        CompilerExpression expression,
        TorchSharpOperatorScanContext context);

    public abstract CompilerResult<CompilerOnnxEmission> PrintOnnx(
        CompilerOperation operation,
        OnnxOperatorPrintContext context);

    public abstract CompilerResult<CompilerTorchSharpExpression> PrintTorchSharp(
        CompilerOperation operation,
        TorchSharpOperatorPrintContext context);
}
```

Each direction should be explicit. The base class may provide a standard unsupported-direction diagnostic for one-way operators, while `Capability` remains the source of truth for which directions are available. Contexts provide phase services but do not decide operator semantics.

Shared families should implement common behavior once and leave concrete operator identity and semantics to small subclasses:

```csharp
internal abstract class BinaryArithmeticOperator : CompilerOperator
{
    protected abstract string CSharpOperatorToken { get; }

    protected abstract string TorchSharpMethodName { get; }

    public override CompilerResult<CompilerOperation> ScanOnnx(
        OnnxNode node,
        OnnxOperatorScanContext context) =>
        context.ScanBinaryNode(this, node);

    public override CompilerResult<CompilerOperation> ScanTorchSharp(
        CompilerExpression expression,
        TorchSharpOperatorScanContext context) =>
        context.ScanBinaryForm(this, expression, TorchSharpMethodName, CSharpOperatorToken);

    public override CompilerResult<CompilerOnnxEmission> PrintOnnx(
        CompilerOperation operation,
        OnnxOperatorPrintContext context) =>
        context.EmitBinaryNode(this, operation);

    public override CompilerResult<CompilerTorchSharpExpression> PrintTorchSharp(
        CompilerOperation operation,
        TorchSharpOperatorPrintContext context) =>
        context.EmitBinaryExpression(operation, CSharpOperatorToken);
}

internal sealed class AddOperator : BinaryArithmeticOperator
{
    public override CompilerOperatorIdentity Identity { get; } =
        new("", "Add");

    public override IReadOnlyCollection<CompilerTorchSharpForm> TorchSharpForms { get; } =
        [CompilerTorchSharpForm.Binary("+"), CompilerTorchSharpForm.Call("torch.add"), CompilerTorchSharpForm.InstanceCall("add")];

    public override CompilerOperationCapability Capability { get; } =
        CompilerOperationCapability.Bidirectional;

    protected override string CSharpOperatorToken => "+";

    protected override string TorchSharpMethodName => "add";
}
```

The example illustrates the intended shape, not mandatory helper names: the arithmetic family owns reusable binary scanning/emission behavior, while `AddOperator` owns Add identity and supported syntax forms. `MulOperator` and other siblings provide their own identity/forms and operation-specific details. ONNX identity matching and TorchSharp-form matching must both resolve to the same operator instance through the registry.

The registry should be assembled from an explicit collection of built-in operator instances, then build validated indexes for ONNX identity and TorchSharp forms. It must fail deterministically on duplicate registrations; it should not use reflection-based class discovery or expose a public plugin API in this task.

## Non-Goals

- Adding operator mappings or expanding their dtype/shape semantics.
- Providing a public API for third-party operator plugins.
- Removing every `if`/`switch` regardless of purpose: eliminate brittle branching, duplication, and operator-specific dispatch, while retaining natural syntax and compiler-phase state checks.

## Implementation Steps

1. Inventory existing mappings, call forms, directional capabilities, validation, and emission, and link each case to its current compiler tests.
2. Define internal operator and phase-context contracts, and register built-in operators explicitly without reflection-based auto-discovery.
3. Implement family base classes and migrate concrete operators while preserving bidirectional semantics and diagnostics.
4. Route the ONNX frontend, TorchSharp frontend, and both backends through the operator registry; remove `CompilerOperatorMapping` and operator-specific dispatch from central compiler files.
5. Audit remaining branches and update architecture documentation and the roadmap to match the final registry and inheritance design.

## Tests

- Preserve and run existing paired mapping tests for ONNX → compiler tree → TorchSharp and TorchSharp → compiler tree → ONNX, including generated source/graph and runtime parity where already covered.
- Verify dispatch by ONNX domain/name and every supported TorchSharp call/operator form, family-base behavior, and duplicate identity/form detection.
- Verify clear diagnostics for unsupported directions, input/attribute configurations, and ambiguous registrations.
- Audit central frontend/backend files to confirm that `CompilerOperatorMapping` and operator-name/family `if`/`switch` dispatch have been removed.
- Run `Onnxify.Compiler.Tests` on net8.0 and net10.0, build all `Onnxify.Compiler` target frameworks, and run `git diff --check`.

## Acceptance Criteria

- Every existing operator mapping is represented by an internal subclass of the shared operator abstraction and preserves its identity, capability, call forms, diagnostics, and runtime behavior.
- ONNX scanning, TorchSharp scanning, ONNX generation, and TorchSharp generation select semantics through operator instances, without central operator-specific `if`/`switch` chains.
- `CompilerOperatorMapping` is removed, and the registry reports duplicate identities/forms deterministically with a clear error.
- Shared operator-family behavior lives in the corresponding base classes; adding a concrete mapping does not require edits to both frontends and backends.
- Public APIs and supported semantics remain unchanged; the compiler and all tests pass on the specified target frameworks.
