## Summary

Extract the non-syntax foundation of TorchSharp deep export from `TorchModuleExportExtensions.cs`.

This task must not attempt to redesign the whole exporter. Its only goal is to create a small, testable foundation that later OXY tasks can build on:

- public facade stays compatible
- decompilation remains where behavior still needs it
- input/output contracts move into a dedicated metadata layer
- runtime module reflection becomes an explicit service
- diagnostics become structured enough for later scanners and printers

## Depends On

None.

## Enables

- `OXY-002`: scanner and IR skeleton
- `OXY-003`: printer skeleton
- `OXY-008`: public extension API

## Current Pain

`TorchModuleExportExtensions.cs` currently mixes:

- public `ExportOnnxModel(...)` overloads
- reading `ModuleInputAttribute` and `ModuleOutputAttribute`
- converting `TensorDimension` into `OnnxTensorType`
- reflection over fields, properties, child modules, and runtime tensors
- graph scope state
- shape/rank/dtype helpers
- diagnostics and thrown exception text
- decompilation and AST interpretation

Before scanning or printing can be modularized, these shared facts must be represented outside the monolithic method walker.

## Goals

- Keep all existing public `ExportOnnxModel(...)` overloads working.
- Move module contract extraction into an internal metadata service.
- Treat explicit input/output arguments and attribute-based contracts as two sources for the same contract model.
- Add runtime metadata collection for safe reflection over the live module instance.
- Add a central shape/dtype resolver used by the existing exporter path.
- Add structured diagnostics without changing public exception types yet.
- Add tests around metadata behavior before changing syntax interpretation.

## Non-Goals

- Do not introduce the final scanner/printer architecture in this task.
- Do not remove the current monolithic AST interpreter.
- Do not migrate Torch operation lowerings.
- Do not expose a broad public extension API yet.
- Do not change emitted ONNX graph structure intentionally.

## Proposed Internal Layout

Create the initial folder structure under `src/Onnxify.TorchSharp`:

```text
DeepExport/
  Diagnostics/
  Metadata/
  Runtime/
  Utilities/
```

Keep types `internal` unless they are already public today.

## Required Types

### DeepExportContext

Create an internal context object that can be used by the current exporter path.

It should contain:

- root TorchSharp module instance
- target `OnnxGraph`
- `OnnxModelCreationOptions`
- resolved module metadata
- diagnostic sink
- shape/dtype resolver

Do not move all exporter state here yet. Keep the existing local dictionaries until later tasks migrate them.

### DeepExportModuleMetadata

Represents facts known before scanning/exporting the method body:

- root module type
- resolved input contract
- resolved output contract
- module fields/properties discovered through reflection
- child modules and stable member names
- runtime TorchSharp tensor shape, dtype, device, and optionally values

### DeepExportContractResolver

Resolves input/output contracts from:

- explicit `ExportOnnxModel(...)` arguments
- `ModuleInputAttribute`
- `ModuleOutputAttribute`

Rules:

- Explicit arguments win over attributes.
- Attribute-based `ExportOnnxModel(options)` must still throw clear errors when required attributes are missing.
- Conflicting metadata should be diagnosed when both explicit and attribute values are present for the same name.
- Symbolic `TensorDimension` values must remain symbolic `OnnxDimension` values.

### DeepExportRuntimeMetadataProvider

Add internal provider-style collection for runtime facts.

Built-in providers:

- reflection provider for fields and properties
- Torch tensor provider for shape, dtype, device, and values when needed
- child module provider
- explicit contract provider
- attribute contract provider

The provider abstraction should be internal for now but shaped so it can become public in `OXY-008`.

### DeepExportShapeTypeResolver

Centralize:

- scalar type to CLR type conversion
- `TensorDimension` to `OnnxDimension` conversion
- TorchSharp tensor dtype to ONNX dtype conversion
- known rank lookup
- known element type lookup
- runtime tensor shape lookup
- diagnostics for unknown or conflicting shape facts

## Implementation Steps

1. Add `DeepExport/Metadata` and `DeepExport/Diagnostics` internal types.
2. Move the logic currently equivalent to `GetModuleInputContract`, `GetModuleOutputContract`, and `ToOnnxTensorType` into the metadata layer.
3. Update `TorchModuleExportExtensions` to call the metadata layer while keeping public behavior unchanged.
4. Add runtime metadata collection for module fields/properties and TorchSharp tensors, but only wire it into existing places where equivalent reflection already happens.
5. Add structured diagnostics internally and convert them to current exception behavior at the public boundary.
6. Keep the current decompilation and AST interpreter in place.

## Tests

Add or update tests in `src/Onnxify.Tests`:

- attribute-based `ExportOnnxModel(options)` reads `ModuleInputAttribute`
- attribute-based `ExportOnnxModel(options)` reads `ModuleOutputAttribute`
- symbolic `TensorDimension` remains symbolic
- fixed `TensorDimension` remains fixed
- explicit input/output metadata still works
- explicit metadata has deterministic precedence over attributes
- missing input/output attributes still produce clear exceptions
- runtime module fields/properties can be discovered without mutating module state
- runtime TorchSharp tensor shape and dtype can be discovered

## Acceptance Criteria

- Existing deep export tests still pass.
- Public API behavior is unchanged.
- Contract extraction no longer lives directly in the public facade methods.
- Runtime metadata collection exists behind an internal service.
- Shape/dtype conversion is centralized enough that later tasks do not need to copy the old helpers.
- The old AST interpreter can still call into the new metadata/resolver layer.

## Risks

- Moving contract resolution can accidentally change public error messages. Keep message intent stable even if exact wording changes.
- Reflection can observe private implementation details. Keep reads deterministic and side-effect free.
- Avoid over-designing the public API here. This task is foundation, not extensibility hardening.
