## Summary

Add compiler-owned mappings for the audited shape-manipulation operators and tensor factories needed by existing compiler use cases.

## Depends On

- [OXY-024](OXY-024.md).
- [OXY-034](OXY-034.md).

## Goals

- Implement the deterministic, compile-time-parameter forms of the audited shape and factory operators from ONNXScript `ops_test_data.py`.
- Use exact typed ONNX operators or exact typed-node subgraphs, preserving symbolic input dimensions when ONNX can represent the shape semantics.
- Keep runtime-computed shape arguments, axes, repeats, and factory dimensions in OXY-035; diagnose those forms explicitly until that task is complete.
- Preserve diagnostics for unsupported overloads, aliasing semantics, dtypes, ranks, and shape constraints.

## Implemented Scope

- ONNX `Flatten` with any valid static axis maps bidirectionally to TorchSharp `torch.flatten(input, start_dim: axis)` and `input.flatten(axis)`. Dynamic axes and `end_dim` values other than `-1` are diagnosed; axes are checked against known input rank.
- ONNX `Transpose` with an explicit valid permutation maps bidirectionally to `Tensor.permute(new long[] { ... })`. Default/null permutations and malformed permutations are diagnosed because the current compiler printer does not resolve rank-dependent default axes.
- ONNX `Reshape` with a statically known int64 shape initializer maps bidirectionally to `torch.reshape`, `Tensor.reshape`, and `Tensor.view`. `allowzero=0` copies input dimensions for zero entries; `allowzero=1` preserves literal zero dimensions. Dynamic shape input can only be printed when `allowzero=1`; TorchSharp scanning requires a static shape array. More than one `-1`, dimensions below `-1`, and `allowzero=1` combining zero with `-1` are diagnosed.
- ONNX `Unsqueeze` maps bidirectionally for exactly one statically known axis through `Tensor.unsqueeze(axis)`. Multi-axis or dynamic axes are rejected by the TorchSharp printer/scanner boundary; generated ONNX axes are stored as an int64 initializer.
- ONNX `Squeeze` with one explicit static axes initializer prints to `Tensor.squeeze(axis)` and preserves runtime values. Export scanning requires static input-rank and selected-dimension metadata to prove the dimension is one; sources without that metadata receive an explicit diagnostic. A compiled-module fixture supplies the shape metadata and verifies the reverse path through ONNX Runtime.
- ONNX `Expand` and `Tile` map to `Tensor.expand` and `Tensor.repeat` for static int64 shape/repeat initializers. Known incompatible dimensions, negative target dimensions, and invalid repeat ranks are rejected. Runtime parity currently covers float32.
- ONNX `Slice` maps to `Tensor.slice` when starts, ends, one axis, and positive step are static int32/int64 initializers. Multi-axis slicing, dynamic bounds, and negative steps are rejected because the currently supported TorchSharp call form cannot preserve them exactly.
- ONNX `Concat` maps to `torch.cat` for a statically known axis and at least two tensor inputs. The TorchSharp scanner accepts an explicit tensor array and static axis.
- ONNX `Split` supports a static int64 split-size initializer and statically declared output count. Its multiple outputs remain ordered through the computation step, generated TorchSharp locals, and tuple return. TorchSharp scanning accepts static sizes; `chunk` and `unbind` lower to Split when input rank and the selected fixed axis dimension prove the exact output count. Dynamic output counts and dynamic split sizes are rejected. Runtime parity currently covers float32.
- `unflatten` is scanned as an exact `Reshape` when the input rank and axis are known and sizes are static; unknown rank and invalid axis/size forms are diagnosed. The generated shape uses ONNX Reshape zero-copy dimensions, preserving runtime-sized dimensions.
- The remaining static scope is still open: audit and implement `stack`, `pad`/`constant_pad_nd`, `flip`, `diagonal`, `repeat_interleave`, `narrow`, `unfold`, `view_as`/`view_copy`, and deterministic tensor/range factories. Runtime-valued arguments are tracked in OXY-035.
- The runtime parity fixtures currently cover `float32`; these shape operators preserve input element type, but a complete runtime dtype matrix has not been added.

## Audited Scope

- The deterministic upstream inventory includes `broadcast_to`, `cat`/`concat`/`concatenate`, `chunk`, `constant_pad_nd`, `diagonal`, `expand`/`expand_as`, `fill`, `flip`, `full`/`full_like`, `new_full`/`new_ones`/`new_zeros`, `ones`/`ones_like`, `permute`, `repeat`/`repeat_interleave`, `narrow`, `split`/`split_with_sizes`, `squeeze`/`squeeze_dim`, `stack`, `tile`, `unbind`, `unflatten`, `unfold`, `view`/`view_as`/`view_copy`, `zeros`/`zeros_like`, `arange` variants, and `slice`. Implemented entries are listed above; all others remain pending their semantic and typed-ONNX representability review.
- `gather`, `index_select`, `select`, and reductions stay in OXY-033. Pointwise broadcast operations stay in OXY-029; `unbind` remains in the OXY-031 audit as a split/collection operation.
- `empty`, `empty_like`, random factories, and `empty_strided` are excluded as nondeterministic or unsupported upstream cases. Complex reinterpretation/view operators and `as_strided` are excluded when ONNX cannot preserve aliasing or storage-view semantics exactly.
- Keep non-pointwise selection/indexing and reductions in OXY-033, pointwise operations in OXY-029, matrix operations in OXY-030, and neural-network operators outside this task.
- Static parameters may be encoded as ONNX attributes or initializers. Runtime-derived shape arguments belong to OXY-035.

## Tests

- Pair tests in both directions for each declared operator and supported shape/dtype case.
- Assert graph/source structure, ONNX Runtime session creation where executable, and deterministic runtime parity.
- Include exact ONNXScript and ONNX Runtime source provenance.
- `Onnxify.Compiler.Tests/ShapeCompilerTests.cs` verifies typed Flatten, Transpose, Reshape, Unsqueeze, and Squeeze behavior. Squeeze covers import/generated TorchSharp execution and ONNX Runtime parity, export with compiled-module shape metadata, and a diagnostic without that metadata.

## Acceptance Criteria

- Every declared case has paired verification or an explicitly tested one-way classification and documented limitation.
