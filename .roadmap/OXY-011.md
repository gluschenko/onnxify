## Summary

Investigate and, if technically useful, add generated `RunAsync` methods to `Onnxify.ModelGenerator` ONNX Runtime inference wrappers.

Generated wrappers currently expose synchronous `Run(...)` methods over `Microsoft.ML.OnnxRuntime.InferenceSession`. ONNX Runtime exposes a real `InferenceSession.RunAsync(...)` API in upstream source, for example around line 1223 of `InferenceSession.shared.cs` at commit `c3a5222d2a80fdad084d128da45e7565ec074a91`: <https://github.com/microsoft/onnxruntime/blame/c3a5222d2a80fdad084d128da45e7565ec074a91/csharp/src/Microsoft.ML.OnnxRuntime/InferenceSession.shared.cs#L1223>.

The expected path is to use that real `InferenceSession.RunAsync(...)` API directly. This task should still verify the exact overload shape available to generated consumer code before implementation.

If ONNX Runtime does not expose a usable async inference overload for the wrapper shape, the implementation must avoid pretending to provide true asynchronous native execution unless there is a clear and documented reason to wrap the call in `Task.Run`.

If implemented, generated async methods should be named `RunAsync` and accept a `CancellationToken cancellationToken = default` parameter.

## Depends On

- Existing `Onnxify.ModelGenerator` ONNX Runtime inference wrapper generation.
- Existing shared generated `OnnxInferenceSessionModelBase` support source from OXY-010.
- Current `Microsoft.ML.OnnxRuntime` API surface available to consuming projects.

## Enables

- Async-friendly application code that consumes generated ONNX Runtime wrappers.
- Consistent cancellation-aware wrapper signatures when callers are already using async pipelines.
- A documented decision about whether generated ONNX Runtime inference can be meaningfully asynchronous.

## Goals

- Verify the exact `Microsoft.ML.OnnxRuntime.InferenceSession.RunAsync(...)` overloads available to generated consumer code.
- If a usable async API exists, generate `RunAsync` overloads that use it directly.
- If no true async API exists, decide explicitly whether to:
  - generate no async methods and document why, or
  - generate `RunAsync` as an opt-in task-scheduler wrapper with clear cancellation limitations.
- When `RunAsync` is generated, include `CancellationToken cancellationToken = default` in the public signatures.
- Preserve the existing synchronous `Run(...)` API shape.
- Keep generated input/output DTO public shape unchanged unless async support requires internal plumbing changes.
- Keep output disposal semantics clear for async results.

## Non-Goals

- Do not change TorchModule generation.
- Do not replace synchronous `Run(...)` methods.
- Do not add a runtime dependency solely to fake asynchronous execution.
- Do not silently claim cancellation can interrupt native inference unless the underlying ONNX Runtime API supports it.
- Do not change model discovery, metadata generation, or `.onnx` MSBuild item behavior.

## Proposed Shape

If supported, generated wrappers should expose async methods analogous to the synchronous overloads:

```csharp
public Task<SampleModelOutputs> RunAsync(
    SampleModelInputs inputs,
    CancellationToken cancellationToken = default
)
```

For wrappers with individual tensor overloads:

```csharp
public Task<SampleModelOutputs> RunAsync(
    Tensor<long> inputIds,
    CancellationToken cancellationToken = default
)
```

If `RunOptions` remains supported in async overloads, prefer an explicit overload rather than ambiguous optional-parameter ordering:

```csharp
public Task<SampleModelOutputs> RunAsync(
    SampleModelInputs inputs,
    RunOptions? runOptions,
    CancellationToken cancellationToken = default
)
```

Use `CancellationToken`, not the misspelled `CancelationToken`.

## Implementation Steps

1. Inspect the current `Microsoft.ML.OnnxRuntime.InferenceSession.RunAsync(...)` API available to generated consumer tests, using the upstream `InferenceSession.shared.cs` source as the starting point, and record the overloads, return type, `RunOptions?` support, and cancellation behavior.
2. Decide whether `RunAsync` should be emitted by default, emitted behind an option, or rejected as misleading. Prefer default emission if the real `InferenceSession.RunAsync(...)` overload supports the generated wrapper needs.
3. If async is implemented, update `OnnxRuntimeInferencePrinter` to emit `RunAsync` overloads matching the existing synchronous overload matrix.
4. If common async helper plumbing is needed, put it in `Templates/OnnxInferenceSessionModelBase.cs` rather than duplicating it per generated model.
5. Ensure generated signatures use named `CancellationToken cancellationToken = default` and include `using System.Threading` and `using System.Threading.Tasks` only when needed.
6. Preserve generated source determinism and avoid overload ambiguity between optional model inputs, `RunOptions?`, and `CancellationToken`.
7. Update `Onnxify.ModelGenerator` release notes if the generated public API changes.

## Tests

Add or update tests in `src/Onnxify.Tests/OnnxModelGeneratorTests.cs` for:

- generated `RunAsync` method signatures for models with required inputs
- generated `RunAsync` method signatures for models with optional inputs
- generated `RunAsync` method signatures for parameterless models
- `CancellationToken cancellationToken = default` appears in each async public overload
- generated async code compiles in a consumer-style test compilation
- generated async code calls `InferenceSession.RunAsync(...)` directly when the real ONNX Runtime async API is available
- synchronous `Run(...)` overloads remain present and unchanged
- no ambiguous overloads are generated when optional tensor inputs and `RunOptions?` are both present

If `RunAsync` is intentionally not implemented, add tests or documentation assertions that lock down the decision if there is a generator option or diagnostic.

## Acceptance Criteria

- The task records the exact `InferenceSession.RunAsync(...)` overload shape used by generated wrappers.
- If implemented, generated ONNX Runtime wrappers expose `RunAsync` methods with `CancellationToken cancellationToken = default`.
- If implemented, generated async methods compile and preserve output disposal expectations.
- If implemented, tests cover required-input, optional-input, and parameterless wrapper shapes.
- If not implemented, the package docs or release notes explain why `RunAsync` is intentionally absent.
- Existing synchronous generated wrapper tests continue to pass.

## Risks

- If the real ONNX Runtime async API is not usable, a `Task.Run`-based fallback could mislead users into expecting native asynchronous inference or reliable cancellation.
- Optional inputs plus optional `RunOptions?` plus optional `CancellationToken` can create confusing overload resolution.
- Returning disposable output wrappers from async methods requires the same disposal discipline as synchronous `Run(...)`.
- ONNX Runtime API availability may differ across package versions used by consumers.
