## Summary

Create a dedicated `Onnxify.Compiler` project that owns the new bidirectional compiler/transpiler feature for C# TorchSharp and ONNX. `Onnxify.ModelGenerator` and `Onnxify.TorchSharp` must depend on this project and expose thin, domain-specific entry points that delegate to it.

The current roadmap treats the two directions as different feature families:

- `deep export`: TorchSharp/C# module structure to ONNX
- `deep import`: ONNX graph structure to generated TorchSharp/C# module code

That split is increasingly artificial. Both directions need the same semantic inventory: graph values, tensor metadata, module state, operator lowering, control-flow representation, diagnostics, and equivalence tests. The durable architecture should be a single intermediate representation and compiler pipeline that can read either side and print either side:

```text
C# TorchSharp module <-> Onnxify compiler IR <-> ONNX graph
```

In blunt terms: if both paths are trying to describe the same computation, they should stop being two separate beasts with two separate registries, two separate mental models, and two separate places to drift. New compiler behavior belongs in `Onnxify.Compiler`, not in either consumer package.

## Package Ownership And Dependency Direction

`Onnxify.Compiler` is the owning project for all new compiler functionality. It contains the compiler IR, computation-tree model, ONNX and C# TorchSharp frontends, C# and ONNX backends, operator mappings, diagnostics, validation primitives, and public orchestration/facade APIs.

The intended project dependency graph is:

```text
Onnxify.Compiler -> Onnxify
Onnxify.ModelGenerator -> Onnxify.Compiler
Onnxify.TorchSharp -> Onnxify.Compiler
```

`Onnxify.Compiler` must not reference `Onnxify.ModelGenerator` or `Onnxify.TorchSharp`. Package-specific projects may provide thin adapters for their existing public types (for example, an adapter that exposes a TorchSharp model as a compiler source), but parsing, lowering, tree transformations, code generation, and ONNX emission remain in `Onnxify.Compiler`. This keeps the dependency graph acyclic and prevents compiler logic from being duplicated in downstream packages.

The compiler API should support operations of this shape:

```csharp
var tree = Compiler.CreateTreeFromOnnx(onnxModel);
var csharp = Compiler.GenerateCSharp(tree);
var onnx = Compiler.GenerateOnnx(tree);
var treeFromTorch = Compiler.CreateTreeFromTorchSharp(torchSource);
```

Exact names and public surface are to be designed during implementation, but the important contract is that tree construction and code generation return compiler-owned models and generated C# program text as a `string`. `Onnxify.ModelGenerator` and `Onnxify.TorchSharp` should delegate to these APIs rather than maintain parallel compiler pipelines.

## Enables

- One canonical place to define TorchSharp/C# and ONNX semantic mappings.
- Less duplicated operator work across `Onnxify.TorchSharp` and `Onnxify.ModelGenerator`.
- Better roundtrip behavior for ONNX -> C# -> ONNX and C# -> ONNX -> C#.
- A cleaner public story: Onnxify can compile/transpile computational scenarios between C# TorchSharp and ONNX in both directions.
- Future tooling that can inspect, normalize, optimize, diff, or explain models at the compiler IR level instead of only at the raw ONNX graph level.

## Goals

- Define a shared compiler IR that can represent the supported intersection of TorchSharp module code and ONNX graphs.
- Make `deep export` and `deep import` become directional frontends/backends over that shared IR instead of separate feature stacks.
- Preserve the current TorchSharp computational-scenario approach: imported ONNX should still generate C# that reconstructs executable TorchSharp modules, as it does today.
- Allow the C# frontend to ingest decompiled TorchSharp `forward(...)` bodies, explicit module metadata, parameters, buffers, helper calls, and supported static control flow.
- Allow the ONNX frontend to ingest graph nodes, initializers, inputs, outputs, value metadata, attributes, and supported subgraphs into the same IR.
- Allow the ONNX backend to emit valid `OnnxGraph` structures from the shared IR.
- Allow the C# backend to emit readable TorchSharp module code from the shared IR.
- Consolidate operator registration so a supported operation declares both parse and print behavior where possible.
- Require every new operator mapping to be verifiable in both directions: `ONNX -> TorchSharp` and `TorchSharp -> ONNX`. An operator may be classified as one-way only when the missing direction is explicitly documented as unsupported or lossy and covered by diagnostics.
- Keep direction-specific escape hatches for semantics that cannot roundtrip cleanly.
- Add architecture documentation that names the unified compiler explicitly and explains how old `deep export` / `deep import` terminology maps to it.

## Non-Goals

- Do not attempt to support arbitrary C# programs.
- Do not promise perfect ONNX -> C# -> ONNX textual identity; runtime and graph semantic equivalence matter more than byte-for-byte graph reproduction.
- Do not remove existing public APIs in the first implementation.
- Do not require every current operator to become bidirectional in one batch.
- Do not turn generated C# into an ONNX Runtime wrapper; this task is about TorchSharp computational reconstruction, not only runtime invocation.
- Do not hide lossy conversions. Unsupported or ambiguous mappings should produce diagnostics and explicit fallback decisions.

## Consolidated Scope From Superseded Deep Export Tasks

The following scope from OXY-001 through OXY-008 remains valid, but its implementation location is now `Onnxify.Compiler` unless it is a deliberately thin adapter for a consumer-specific public type:

- Compiler-owned metadata services resolve explicit and attribute-based input/output contracts, module members, child modules, runtime tensor shape/dtype/device facts, symbolic dimensions, and conflicting facts without scattered reflection.
- The computation tree supports ordered blocks, declarations, assignments, returns, references, literals, tensor method calls, binary/unary expressions, arrays, tuples, deconstruction, indexers, static conditionals, validation/no-grad scopes, and safe static iteration. Dynamic control flow is diagnosed unless explicitly supported.
- Ordered scanner and printer registries use deterministic, most-specific-first dispatch, report no-match and ambiguous-match diagnostics, and preserve a compatibility fallback for syntax that has not yet migrated.
- Helper and module boundaries preserve child scopes, parameter binding, return values, tuple/array ordering, generated helper recognition, known module `forward` calls, sequential traversal, recursive user modules, and caller/callee names in diagnostics.
- Operator mappings are migrated by semantic family where useful: matrix multiplication; activations and elementwise functions; reshape/view/flatten/permute/transpose/unsqueeze/squeeze/slice/gather; reductions/comparisons/casts; tensor and like-factory operations; random factories; collection/selection operations; and functional neural-network operations such as convolution, padding, batch normalization, adaptive pooling, and interpolation.
- The public compiler extension surface may provide narrow contracts for metadata providers, module exporters, scanners, printers, and method lowerings, with deterministic priority, strict/permissive diagnostics, optional debug IR, and runtime metadata controls. Existing package overloads remain compatible and delegate to the compiler.
- Each migrated operator family requires structural checks, ONNX Runtime session validation, and deterministic TorchSharp-versus-ONNX Runtime numerical parity where executable. Every new operator must additionally have paired directional verification: `ONNX -> TorchSharp` and `TorchSharp -> ONNX`.

## Proposed Architecture

Introduce a dedicated project, `src/Onnxify.Compiler/`, for the compiler feature:

```text
src/
  Onnxify.Compiler/
    Ir/
    Frontends/
      CSharpTorch/
      OnnxGraph/
    Backends/
      CSharpTorch/
      OnnxGraph/
    Operators/
    Diagnostics/
    Validation/
```

Do not start the feature inside `Onnxify.ModelGenerator` or `Onnxify.TorchSharp` with a later extraction plan. The project boundary is part of this task: add `Onnxify.Compiler` to the solution, make the two consumer projects reference it, and keep their integration layers thin.

Pipeline shape:

```text
CSharpTorchFrontend -> Compiler IR -> OnnxGraphBackend
OnnxGraphFrontend   -> Compiler IR -> CSharpTorchBackend
```

The IR should represent:

- tensors, scalar constants, optional values, sequences, and tuples
- symbolic and fixed dimensions
- parameters, buffers, and initializers
- module calls and reusable computation blocks
- operator applications with normalized attributes
- graph inputs, outputs, and intermediate values
- supported static control flow
- diagnostics and source spans back to either C# syntax or ONNX graph nodes

## Implementation Steps

1. Inventory current `deep export` and `deep import` types, registries, tests, and terminology.
2. Add `src/Onnxify.Compiler/` to the solution with a dependency only on the core `Onnxify` project; add project references from `Onnxify.ModelGenerator` and `Onnxify.TorchSharp`.
3. Define the minimal compiler-owned IR/computation-tree model needed to represent current covered roundtrip tests.
4. Define compiler-owned source/sink contracts for package-specific inputs, including a TorchSharp source adapter, without referencing consumer projects from `Onnxify.Compiler`.
5. Build an ONNX graph frontend that can import a tiny supported graph into the shared tree.
6. Build an ONNX graph backend that can print the same tree back to `OnnxGraph`.
7. Build a C# TorchSharp backend that can print the same tree as generated TorchSharp module code and return that code as a `string`.
8. Adapt one existing `deep import` operator and one existing `deep export` operator to use the shared compiler-owned operator mapping.
9. For every new operator mapping, add verification from both starting points: ONNX imported into TorchSharp and TorchSharp lowered to ONNX. Compare generated structure and runtime behavior where executable.
10. Move the existing decompiler/scanner integration behind the compiler contracts; leave only compatibility façades and thin TorchSharp/ModelGenerator adapters in the consumer projects.
11. Add bidirectional roundtrip tests for both starting points: C# -> ONNX -> C# and ONNX -> C# -> ONNX.
12. Document migration rules for future operators so contributors add mappings in `Onnxify.Compiler`, provide both directional verification cases, and classify the mapping as bidirectional, export-only, import-only, or unsupported.
13. Keep existing public APIs as façades that call into the unified compiler pipeline, and mark old direction-specific registries as compatibility or migration surfaces.

## Acceptance Criteria

- The repository has a documented unified compiler/transpiler architecture for C# TorchSharp <-> ONNX, owned by the `Onnxify.Compiler` project.
- `Onnxify.ModelGenerator` and `Onnxify.TorchSharp` reference `Onnxify.Compiler`, while `Onnxify.Compiler` has no reverse dependency on either consumer.
- At least one operator path is implemented through shared bidirectional compiler mapping rather than duplicated import/export logic.
- Existing `deep export` and `deep import` public APIs still work.
- New code can explain whether an operation is bidirectional, export-only, import-only, or unsupported.
- Every new operator is verifiable in both `ONNX -> TorchSharp` and `TorchSharp -> ONNX` directions, or has an explicit unsupported/lossy classification with diagnostics and tests.
- At least one ONNX -> C# -> ONNX roundtrip and one C# -> ONNX -> C# roundtrip are covered by automated tests.
- Contributor docs explain that future operator work should prefer the unified compiler mapping when possible.

## Risks

- Consolidating the former staged deep-export work into one compiler task may require implementation sequencing inside OXY-019, even though the roadmap tasks themselves are no longer separate execution units.
- Some TorchSharp constructs do not have clean ONNX equivalents, and some ONNX graph patterns do not reconstruct into pleasant TorchSharp code.
- Forcing every operator into a symmetric abstraction can overfit the common case. Keep one-way mappings explicit.
- A new project boundary may create package dependency problems between `Onnxify.TorchSharp`, `Onnxify.ModelGenerator`, and core `Onnxify`.
- If `Onnxify.Compiler` directly references TorchSharp or ModelGenerator, the dependency graph can become cyclic. Keep consumer-specific model access behind compiler-owned contracts and thin adapters.
- Generated C# readability can regress if the IR is too ONNX-shaped. Preserve TorchSharp-friendly module structure where the ONNX graph contains enough information.
