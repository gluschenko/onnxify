## Summary

Replace the conceptual split between `deep export` and `deep import` with one bidirectional compiler/transpiler architecture for C# and ONNX.

The current roadmap treats the two directions as different feature families:

- `deep export`: TorchSharp/C# module structure to ONNX
- `deep import`: ONNX graph structure to generated TorchSharp/C# module code

That split is increasingly artificial. Both directions need the same semantic inventory: graph values, tensor metadata, module state, operator lowering, control-flow representation, diagnostics, and equivalence tests. The durable architecture should be a single intermediate representation and compiler pipeline that can read either side and print either side:

```text
C# TorchSharp module <-> Onnxify compiler IR <-> ONNX graph
```

In blunt terms: if both paths are trying to describe the same computation, they should stop being two separate beasts with two separate registries, two separate mental models, and two separate places to drift.

## Depends On

- Current `deep export` roadmap tasks `OXY-001` through `OXY-008`.
- Existing `Onnxify.ModelGenerator` TorchModule generation path.
- Existing `DeepImportExportParityTests` roundtrip test infrastructure.
- Existing `Onnxify.TorchSharp` operator export coverage and ModelGenerator operator import registries.

## Enables

- One canonical place to define TorchSharp/C# and ONNX semantic mappings.
- Less duplicated operator work across `Onnxify.TorchSharp` and `Onnxify.ModelGenerator`.
- Better roundtrip behavior for ONNX -> C# -> ONNX and C# -> ONNX -> C#.
- A cleaner public story: Onnxify can compile/transpile computational scenarios between C# TorchSharp and ONNX in both directions.
- Future tooling that can inspect, normalize, optimize, diff, or explain models at the compiler IR level instead of only at the raw ONNX graph level.

## Goals

- Define a shared compiler IR that can represent the supported intersection of TorchSharp module code and ONNX graphs.
- Make `deep export` and `deep import` become directional frontends/backends over that shared IR instead of separate feature stacks.
- Preserve the current TorchSharp computational-scenario approach: imported ONNX should still generate C# that reconstructs executable TorchSharp modules, as it does today.
- Allow the C# frontend to ingest decompiled TorchSharp `forward(...)` bodies, explicit module metadata, parameters, buffers, helper calls, and supported static control flow.
- Allow the ONNX frontend to ingest graph nodes, initializers, inputs, outputs, value metadata, attributes, and supported subgraphs into the same IR.
- Allow the ONNX backend to emit valid `OnnxGraph` structures from the shared IR.
- Allow the C# backend to emit readable TorchSharp module code from the shared IR.
- Consolidate operator registration so a supported operation declares both parse and print behavior where possible.
- Keep direction-specific escape hatches for semantics that cannot roundtrip cleanly.
- Add architecture documentation that names the unified compiler explicitly and explains how old `deep export` / `deep import` terminology maps to it.

## Non-Goals

- Do not attempt to support arbitrary C# programs.
- Do not promise perfect ONNX -> C# -> ONNX textual identity; runtime and graph semantic equivalence matter more than byte-for-byte graph reproduction.
- Do not remove existing public APIs in the first implementation.
- Do not require every current operator to become bidirectional in one batch.
- Do not turn generated C# into an ONNX Runtime wrapper; this task is about TorchSharp computational reconstruction, not only runtime invocation.
- Do not hide lossy conversions. Unsupported or ambiguous mappings should produce diagnostics and explicit fallback decisions.

## Proposed Architecture

Introduce a shared internal compiler namespace, for example:

```text
src/
  Onnxify.Compiler/
    Ir/
    Frontends/
      CSharpTorch/
      OnnxGraph/
    Backends/
      CSharpTorch/
      OnnxGraph/
    Operators/
    Diagnostics/
    Validation/
```

If a new project is too large for the first step, start with internal folders under the owning package and extract later. The important decision is the semantic boundary, not the first physical folder name.

Pipeline shape:

```text
CSharpTorchFrontend -> Compiler IR -> OnnxGraphBackend
OnnxGraphFrontend   -> Compiler IR -> CSharpTorchBackend
```

The IR should represent:

- tensors, scalar constants, optional values, sequences, and tuples
- symbolic and fixed dimensions
- parameters, buffers, and initializers
- module calls and reusable computation blocks
- operator applications with normalized attributes
- graph inputs, outputs, and intermediate values
- supported static control flow
- diagnostics and source spans back to either C# syntax or ONNX graph nodes

## Implementation Steps

1. Inventory current `deep export` and `deep import` types, registries, tests, and terminology.
2. Decide whether the shared compiler IR starts inside an existing project or a new internal project.
3. Define the minimal IR needed to represent current covered roundtrip tests.
4. Build an ONNX graph frontend that can import a tiny supported graph into the shared IR.
5. Build an ONNX graph backend that can print the same IR back into `OnnxGraph`.
6. Build a C# TorchSharp backend that can print the same IR as generated TorchSharp module code.
7. Adapt one existing `deep import` operator and one existing `deep export` operator to use the shared operator mapping.
8. Add a C# TorchSharp frontend adapter around the existing decompiler/scanner path, initially for the same minimal IR subset.
9. Add bidirectional roundtrip tests for both starting points: C# -> ONNX -> C# and ONNX -> C# -> ONNX.
10. Document migration rules for future operators so contributors add bidirectional compiler mappings when semantics allow it.
11. Keep existing public APIs as facades that call into the unified compiler pipeline.
12. Mark old direction-specific registries as compatibility or migration surfaces once equivalent compiler mappings exist.

## Tests

- Existing `deep export` tests continue to pass through the public API.
- Existing `deep import` / generated TorchModule tests continue to pass through the public API.
- New tests cover at least one minimal ONNX graph imported into IR and printed back to ONNX.
- New tests cover at least one minimal ONNX graph imported into IR and printed as TorchSharp module code.
- New tests cover at least one minimal TorchSharp module scanned into IR and printed to ONNX.
- Roundtrip tests compare runtime behavior through ONNX Runtime and TorchSharp where executable.
- Diagnostics tests prove unsupported one-way mappings fail clearly instead of silently producing broken code or graphs.

## Acceptance Criteria

- The repository has a documented unified compiler/transpiler architecture for C# TorchSharp <-> ONNX.
- At least one operator path is implemented through shared bidirectional compiler mapping rather than duplicated import/export logic.
- Existing `deep export` and `deep import` public APIs still work.
- New code can explain whether an operation is bidirectional, export-only, import-only, or unsupported.
- At least one ONNX -> C# -> ONNX roundtrip and one C# -> ONNX -> C# roundtrip are covered by automated tests.
- Contributor docs explain that future operator work should prefer the unified compiler mapping when possible.

## Risks

- The existing roadmap may need to be re-sequenced if the shared IR should replace parts of `OXY-002` and `OXY-003`.
- Some TorchSharp constructs do not have clean ONNX equivalents, and some ONNX graph patterns do not reconstruct into pleasant TorchSharp code.
- Forcing every operator into a symmetric abstraction can overfit the common case. Keep one-way mappings explicit.
- A new project boundary may create package dependency problems between `Onnxify.TorchSharp`, `Onnxify.ModelGenerator`, and core `Onnxify`.
- Generated C# readability can regress if the IR is too ONNX-shaped. Preserve TorchSharp-friendly module structure where the ONNX graph contains enough information.
