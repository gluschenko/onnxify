## Summary

Make `Onnxify.SourceGenerator` generate fully typed operator input and output fields instead of broad or weakly typed field representations.

Generated operator models should expose input and output fields with types that reflect ONNX operator schemas as closely as practical. This task should evaluate whether union-style typing, such as `OneOf`, custom discriminated union structs, or generated type wrappers, is the right shape for schema cases where an input or output accepts multiple ONNX type constraints.

## Depends On

- Existing `Onnxify.SourceGenerator` schema parsing and generated model output.
- Existing generated ONNX operator metadata and any linked schema models.
- Current `Onnxify` operator, graph, tensor, and value model types.
- Current downstream consumers of generated operator definitions.

## Enables

- Safer operator construction APIs with compile-time guidance for valid input and output value types.
- Better generated documentation and IntelliSense for operator inputs and outputs.
- Fewer runtime validation failures caused by passing structurally invalid values to generated operators.
- Stronger foundations for future graph builders, model generators, and TorchSharp import/export features.

## Goals

- Audit the current generated operator input/output field types and identify where schema information is lost.
- Map ONNX type constraints into generated C# types for required, optional, variadic, homogeneous, and heterogeneous inputs/outputs.
- Decide whether to use an external `OneOf` package, a repository-owned union abstraction, generated per-operator wrappers, or another approach.
- Preserve ergonomic construction for common single-type inputs such as tensors.
- Represent optional and variadic inputs/outputs clearly without confusing nullability, empty sequences, and omitted values.
- Keep generated code deterministic and compatible with the repository's target frameworks.
- Update source-generator tests and generated-artifact refresh workflow as needed.

## Non-Goals

- Do not change ONNX schema semantics.
- Do not make generated types so strict that valid dynamic or symbolic ONNX graphs become impossible to construct.
- Do not add a new third-party dependency such as `OneOf` without explicitly evaluating package footprint, target framework compatibility, and public API consequences.
- Do not hand-edit generated operator artifacts when generator code owns them.
- Do not redesign unrelated graph serialization or tensor storage APIs unless typed fields require a small supporting abstraction.

## Typing Questions

Resolve these design questions before implementation:

- Should multi-type inputs use `OneOf<T1, T2, ...>`, a custom `OnnxValueUnion`, generated per-field union types, or a looser common interface?
- How should ONNX optional inputs be represented: nullable typed values, explicit optional wrappers, or omitted inputs in a builder API?
- How should variadic inputs be represented when the variadic group has one type constraint versus several possible type constraints?
- Should generated output fields be typed as produced values, output descriptors, or symbolic graph values?
- How should type parameters or constraints be named when ONNX schema aliases such as `T`, `T1`, and `Tind` appear in operator definitions?
- How much backward compatibility should be preserved for existing generated operator constructors and properties?

## Implementation Steps

1. Inspect current generated operator field output and source-generator templates/services that produce operator input and output members.
2. Build a small taxonomy of ONNX schema input/output patterns from representative operators:
   - single required tensor input
   - optional tensor input
   - variadic homogeneous input
   - multi-type constrained input
   - sequence/map/optional ONNX value types
   - multiple outputs with different constraints
3. Choose the typed representation strategy and record the decision in the worklog before broad implementation.
4. Implement the smallest shared abstractions needed for typed fields, preferring repository-owned types if public API stability matters.
5. Update `Onnxify.SourceGenerator` to emit typed input and output fields from schema constraints.
6. Refresh generated artifacts through the owning generator workflow.
7. Update tests to assert representative generated code shape and compilation.
8. Update package docs or release notes if public generated APIs change.

## Tests

Add or update tests for:

- generated required single-type input fields
- generated optional input fields
- generated variadic input fields
- generated fields with multiple allowed type constraints
- generated outputs with distinct type constraints
- generated code compiles for representative operators
- generated APIs reject invalid value types at compile time where feasible
- generated artifacts are deterministic across repeated generator runs
- backward compatibility aliases or migration behavior, if retained

## Acceptance Criteria

- The task records a clear decision on `OneOf` versus a repository-owned or generated union representation.
- Generated operator input and output fields preserve ONNX schema type information materially better than the current implementation.
- Representative generated operators compile and have ergonomic typed construction paths.
- Optional and variadic fields have documented and tested behavior.
- Source-generator tests cover the main schema typing patterns.
- Generated artifacts are refreshed only through the owning generator workflow.
- Any public API impact is reflected in docs or release notes.

## Risks

- Fully typed fields can create a large public API surface and may make future schema changes harder to absorb.
- External union libraries can add dependency and compatibility concerns to core packages.
- Overly strict typing can block valid ONNX graphs with dynamic or symbolic types.
- Variadic and optional ONNX schema semantics can be subtle; poor representation could make the API harder to use than the current looser shape.
- Refreshing generated artifacts may create a large diff. Keep generator changes reviewed separately from mechanical output where practical.
