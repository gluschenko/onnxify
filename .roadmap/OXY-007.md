## Summary

Move Torch tensor, factory, functional, and module operation lowerings behind semantic IR nodes and printers.

This task is operator-focused. It should not introduce new syntax infrastructure except where a specific operation family needs a small semantic node.

## Depends On

- `OXY-001`: metadata and shape/type resolver
- `OXY-002`: scanner and IR skeleton
- `OXY-003`: printer skeleton
- `OXY-004`: basic data flow
- `OXY-005`: shapes, arrays, tuples, and static control flow
- `OXY-006`: helper/module call migration

## Enables

- `OXY-008`: fallback removal and public operation lowerings

## Goals

- Migrate existing Torch operation coverage family by family.
- Use semantic IR nodes for known Torch operations instead of generic invocation spaghetti.
- Delegate graph emission to `TorchTensorOperatorExtensions` and `TorchModuleExtensions` where possible.
- Add parity tests for each migrated family.
- Reduce operator-specific logic in `TorchModuleExportExtensions.cs`.

## Non-Goals

- Do not port brand-new ONNXScript operators as part of this task unless needed to preserve existing behavior.
- Do not redesign `TorchTensorOperatorExtensions`.
- Do not finalize public operation-lowering APIs.
- Do not batch all operators into one unreviewable change.

## Attribute Coverage

When migrating a converter that corresponds to ONNXScript/Torch operator coverage:

- keep `[TorchOp(...)]` attributes aligned
- do not hand-edit generated converter docs
- refresh observer/docs only when actual coverage changes

## Tests

For each operation family:

- focused structural graph assertions
- ONNX Runtime session creation
- eager vs ONNX Runtime numerical parity when deterministic
- unsupported case diagnostics for intentionally unsupported overloads

## Acceptance Criteria

- Existing deep export operation tests run through semantic operation IR/printers.
- `TorchModuleExportExtensions.cs` no longer owns migrated operator lowerings.
- Each migrated family has focused tests.
- No operation family is migrated only by graph-shape assertions when runtime parity is feasible.
- Generated docs workflow remains aligned when `[TorchOp(...)]` coverage changes.

## Risks

- Operator migration can silently change numerical behavior. Pair structure tests with runtime parity.
- Random operations cannot use simple value parity. Validate graph legality and deterministic attributes instead.
- Semantic operation nodes can become too granular. Keep families coherent and delegate shared graph emission.
