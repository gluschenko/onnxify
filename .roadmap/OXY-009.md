# OXY-009: TorchSharp Export Runtime Evaluation

## Summary

Add a runtime evaluation feature to `Onnxify.TorchSharp` that verifies an exported `OnnxModel` against the original TorchSharp module on the same representative inputs.

The feature should create an ONNX Runtime inference session for the exported model, run the original `TorchModule` on the same test data, compare outputs, and return an evaluation result that contains loss metrics, per-output comparison details, and enough diagnostics to understand mismatches.

## Depends On

- Existing `Onnxify.TorchSharp` export APIs that produce an `OnnxModel`.
- Existing tensor conversion helpers in `Onnxify.TorchSharp`.

## Enables

- Safer TorchSharp-to-ONNX export workflows.
- Reusable eager-vs-runtime parity tests for future operator work.
- Package documentation that can recommend evaluation checks after export.

## Goals

- Add `Microsoft.ML.OnnxRuntime.Managed` to `Onnxify.TorchSharp` at exactly version `1.27.0`.
- Introduce a public evaluation API that accepts an exported `OnnxModel` and the original `TorchModule`.
- Support strongly typed module/input/output shapes where practical, likely through two generic type arguments for the evaluated model/module surfaces.
- Return an `EvaluationResult<TTorchModule, TOnnxModel>` or similarly named public result type that contains aggregate loss and detailed comparison data.
- Support caller-provided test data.
- Support caller-provided collections of one or more test samples/batches.
- Provide sensible default loss calculation for tensor outputs.
- Allow callers to plug in custom loss/comparison logic when default numeric comparison is insufficient.
- Include clear diagnostics for unsupported input or output shapes, dtype mismatches, missing ONNX inputs/outputs, and runtime execution failures.

## Non-Goals

- Do not redesign the existing export pipeline.
- Do not make ONNX Runtime a dependency of the core `Onnxify` package.
- Do not hide numerical incompatibilities by silently relaxing tolerances.
- Do not require all TorchSharp modules to use one fixed input or output type.
- Do not implement training-mode or gradient comparison semantics.
- Do not build a full benchmark runner as part of this task.

## API Shape

Start with a small public surface in `Onnxify.TorchSharp`.

Suggested result shape:

```csharp
public sealed class EvaluationResult<TTorchModule, TOnnxModel>
{
    public TTorchModule TorchModule { get; }

    public TOnnxModel OnnxModel { get; }

    public double Loss { get; }

    public IReadOnlyList<EvaluationSampleResult> Samples { get; }

    public IReadOnlyList<EvaluationDiagnostic> Diagnostics { get; }

    public bool Passed { get; }
}
```

Suggested API shape:

```csharp
public static EvaluationResult<TTorchModule, OnnxModel> Evaluate<TTorchModule, TInput>(
    this TTorchModule torchModule,
    OnnxModel onnxModel,
    IReadOnlyList<TInput> inputs,
    TorchExportEvaluationOptions? options = null
)
    where TTorchModule : torch.nn.Module;
```

If the implementation needs both source and exported model type parameters, prefer a naming pattern like:

```csharp
public sealed class EvaluationResult<TSourceModel, TExportedModel>
```

Callers that need to evaluate a single sample should pass a one-element collection instead of using a separate single-sample overload.

Keep the API discoverable from the current TorchSharp export entry points.

## Options

Add options for:

- ONNX Runtime session options.
- input name mapping when graph input names do not match inferred TorchSharp names.
- output name mapping.
- absolute and relative tolerance thresholds.
- failure policy: collect diagnostics vs throw on first failure.
- custom loss/comparison delegate.
- device and dtype normalization policy for TorchSharp eager execution.
- temporary model serialization strategy for creating the ONNX Runtime session from an `OnnxModel`.

## Implementation Steps

1. Add `Microsoft.ML.OnnxRuntime.Managed` version `1.27.0` to `src/Onnxify.TorchSharp/Onnxify.TorchSharp.csproj`.
2. Inspect existing `OnnxModel.Save(...)` stream/file APIs and choose an in-memory or temporary-file path for constructing `InferenceSession`.
3. Add internal adapters that convert supported TorchSharp inputs into ONNX Runtime `NamedOnnxValue` inputs.
4. Add internal adapters that convert ONNX Runtime outputs and TorchSharp eager outputs into comparable tensor views.
5. Implement collection-based evaluation for one or more samples.
6. Aggregate loss across samples while preserving per-sample details.
7. Add public result, sample-result, output-result, diagnostic, and options types.
8. Add public extension methods near the existing TorchSharp export facade.
9. Document unsupported cases with explicit diagnostics or exceptions.
10. Update package docs and release notes for `Onnxify.TorchSharp`.

## Loss And Comparison Semantics

Default behavior should compare deterministic numeric tensor outputs.

Recommended built-in metrics:

- mean squared error as the aggregate `Loss`
- maximum absolute error per output
- mean absolute error per output
- element count and shape per output
- pass/fail against configured tolerance

The default comparer should reject or diagnose:

- different output counts
- missing named outputs
- incompatible shapes
- unsupported dtypes
- NaN/Infinity mismatches unless explicitly allowed by options

## Tests

Add focused tests in `src/Onnxify.Tests` for:

- project reference restores with `Microsoft.ML.OnnxRuntime.Managed` exactly `1.27.0`
- simple deterministic module evaluation passes with low loss
- deliberate output mismatch fails and reports diagnostics
- one-element input collection
- multiple input samples
- named input mapping
- named output mapping
- tolerance configuration
- unsupported dtype or shape diagnostics
- custom comparer/loss delegate is invoked
- ONNX Runtime session creation uses the exported `OnnxModel`

Prefer small deterministic modules already covered by export tests. Avoid random modules unless their seeds and generated values are fully controlled.

## Acceptance Criteria

- `Onnxify.TorchSharp` references `Microsoft.ML.OnnxRuntime.Managed` exactly `1.27.0`.
- The public evaluation API can compare an exported `OnnxModel` and original TorchSharp module on the same test input data.
- The API accepts one or more test samples through the same collection-based input surface.
- Evaluation results include aggregate loss, per-sample/per-output comparison details, pass/fail status, and diagnostics.
- Callers can provide custom test data and custom comparison logic.
- Focused automated tests cover successful parity and failure diagnostics.
- Package docs and release notes describe the new feature.

## Risks

- Adding ONNX Runtime increases the dependency footprint of `Onnxify.TorchSharp`; keep it out of `Onnxify`.
- TorchSharp and ONNX Runtime dtype/device conventions can differ. Normalize explicitly and diagnose unsupported cases.
- Dynamic shapes and multi-input/multi-output modules can complicate default mapping. Make mappings configurable.
- Some exports are nondeterministic or numerically unstable. Default docs should recommend deterministic modules and representative fixed test data.
- Creating `InferenceSession` may require serializing the model. Keep temporary resources deterministic and clean up reliably.
