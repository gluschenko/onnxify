## Summary

Add a durable validation workflow that can test ONNX models generated by Onnxify across CUDA 10, CUDA 11, CUDA 12, and CUDA 13 execution environments.

The goal is to catch provider-specific ONNX Runtime behavior, CUDA package compatibility issues, missing GPU kernels, and generated-model assumptions that are invisible in CPU-only tests. The workflow should be usable locally and in CI environments that provide NVIDIA GPUs. GitHub-hosted runners do not currently provide CUDA-capable GPUs by default, so the first implementation should make GPU validation opt-in for self-hosted runners or containerized GPU machines instead of making normal PR CI depend on unavailable hardware.

## Depends On

- Existing generated ONNX model smoke and parity tests in `src/Onnxify.Tests`.
- Existing `OnnxRuntimeCompatibilityAssert` session creation helper.
- A selected strategy for installing compatible `Microsoft.ML.OnnxRuntime.Gpu` or native ONNX Runtime CUDA provider assets per CUDA major version.
- Access to at least one CUDA-capable validation environment, either local, self-hosted GitHub Actions runner, or another CI provider with NVIDIA GPU support.
- A decision on which CUDA 10 and CUDA 13 combinations are realistically supported by the available ONNX Runtime and NVIDIA package matrix.

## Enables

- Confidence that generated ONNX graphs are not only CPU-runtime valid but also GPU-runtime valid.
- Early detection of CUDA provider packaging drift before publishing packages.
- Safer TorchSharp deep-export work when generated models rely on operators with different CPU and CUDA kernel coverage.
- A foundation for validating large generated model wrappers on GPU without bloating ordinary unit-test runs.

## Goals

- Create a GPU validation test profile that runs a focused generated-model corpus through ONNX Runtime with the CUDA execution provider.
- Cover CUDA major versions 10, 11, 12, and 13 where compatible ONNX Runtime GPU packages or containers exist.
- Make unsupported version combinations explicit in configuration and output rather than silently passing or failing with unclear loader errors.
- Reuse existing generated ONNX model fixtures where possible, then add a small provider-sensitive corpus if needed.
- Validate both session creation and at least one deterministic inference run for each selected model.
- Report provider metadata, CUDA runtime version, NVIDIA driver version, ONNX Runtime version, and loaded execution providers in test output.
- Add a local command or script that developers can run against one CUDA environment at a time.
- Add an opt-in CI workflow or CI job matrix that targets self-hosted GPU runners without blocking the existing CPU-only `build-test` job.
- Preserve CPU-only test behavior for normal contributors without NVIDIA hardware.
- Document how to provision or select the CUDA environment for each matrix entry.

## Non-Goals

- Do not require normal pull request CI to have NVIDIA hardware.
- Do not promise CUDA 10 or CUDA 13 coverage if current ONNX Runtime GPU packages cannot support those versions; record the gap and keep the matrix entry skipped with a clear reason.
- Do not benchmark model throughput or latency in this task.
- Do not add large downloaded model files to the repository.
- Do not replace CPU ONNX Runtime compatibility tests.
- Do not make generated wrappers depend on CUDA-specific APIs.
- Do not hide provider initialization failures behind broad test skips when the selected environment claims to support that CUDA version.

## Implementation Steps

1. Inventory the current ONNX Runtime GPU package support matrix and map it to CUDA 10, 11, 12, and 13.
2. Define the supported matrix as data, including package version, CUDA major version, expected provider name, container image or runner label, and skip reason when unsupported.
3. Add a GPU-specific test category or trait so CUDA validation can be selected independently from ordinary unit tests.
4. Extend or wrap `OnnxRuntimeCompatibilityAssert` so tests can create sessions with CUDA provider options and can report loaded provider diagnostics.
5. Build a minimal generated-model corpus that exercises common generated wrappers and deep-export graphs without requiring large external assets.
6. Add deterministic inference assertions for models where representative inputs and outputs are stable.
7. Add a local script, for example under `scripts/`, that restores the selected GPU package set and runs only the CUDA validation profile.
8. Add an opt-in GitHub Actions workflow or job using self-hosted GPU runner labels such as `cuda-10`, `cuda-11`, `cuda-12`, and `cuda-13`.
9. Upload test logs and provider diagnostics as workflow artifacts for failed GPU runs.
10. Document setup requirements, expected skips, and the difference between CPU compatibility tests and CUDA provider validation.

## Tests

- Unit tests should continue to run without CUDA hardware and without referencing GPU-only packages by default.
- CUDA validation tests should fail clearly when CUDA provider loading is expected but unavailable.
- CUDA validation tests should skip clearly when a matrix entry is intentionally unsupported by the selected ONNX Runtime package version.
- Generated ONNX models should be tested through ONNX Runtime CUDA session creation.
- At least one generated model should run inference and compare deterministic output values on each supported CUDA major version.
- CI configuration should be validated with workflow syntax checks or a dry-run equivalent where possible.

## Acceptance Criteria

- A developer can run one documented command for a selected CUDA major version and get GPU validation results.
- The CUDA matrix includes entries for CUDA 10, 11, 12, and 13, with either executable configuration or an explicit unsupported reason for each entry.
- The existing CPU-only CI path remains unchanged for contributors without GPUs.
- GPU validation records ONNX Runtime version, CUDA environment details, and loaded execution providers in logs.
- At least one generated ONNX Runtime wrapper and one TorchSharp deep-export generated model are included in the GPU validation corpus when their operators have CUDA kernels.
- Provider initialization failures include enough context to distinguish missing native libraries, driver mismatch, unsupported CUDA version, and missing ONNX Runtime CUDA kernels.

## Risks

- ONNX Runtime GPU package support may not span CUDA 10 through CUDA 13 at the same ONNX Runtime version, requiring separate package versions or explicit unsupported entries.
- CUDA 10 may require older operating system images, older drivers, or older ONNX Runtime packages that conflict with current .NET and repository dependencies.
- CUDA 13 support may lag in ONNX Runtime packages and need to remain documented as a future matrix slot until upstream support exists.
- Self-hosted runner labels and GPU provisioning can become repository-specific; keep the workflow configurable instead of baking in one machine layout.
- Native provider loading errors are often noisy and platform-specific; the test harness should capture enough diagnostics to make failures actionable.
